# F1.31 Where files are kept

Status: spec'd for 0.6.0 ([#306](https://github.com/APRS-NET/AprsMap/issues/306)), decisions agreed 2026-10-19
(maintainer request). Not built.

## User story

As a user, I can see in Help › About where the app keeps my settings, my message history and its downloads, and copy
each path in one click, to back them up, read a file, or tell someone helping me. When something goes wrong, there's a
log I can send, even though I started the app from its menu entry and not from a terminal. As a gateway operator, I see
where the server keeps its files; my viewers don't.

## Background: what already exists

- The desktop app keeps its files in each system's own folders (F4.15 behavior 13, `AppFolders`): **Settings**
  (profiles, sources, appearance, layouts), **Data** (message history, packet captures), **Cache** and, read only,
  **defaults for every user**. Map tiles have their own cache folder (`Tiles:CacheFolder`, by default the system's cache
  folder). `Engine:SettingsFolder` and `Engine:DataFolder` move the first two.
- The gateway keeps its files where its configuration puts them: the container's `/data` volume by default
  (deployment.md).
- Help › About (F1.29 behavior 10) shows the versions, the connection, the licence and the credits.
- The desktop app logs only to the terminal it was started from, so an app started from its menu entry or as an
  AppImage leaves no log.

## Behavior

### Files in About

1. Help › About has a **Files** part listing the folders the app uses, folders only (maintainer, 2026-10-19), each with
   its name, what it holds, its full path and a **Copy** button:
   1. **Settings**: profiles, sources, appearance and layouts.
   2. **Data**: message history and packet captures.
   3. **Map tiles**: downloaded map tiles (and the downloaded device list, F4.16, in the cache folder).
   4. **Logs**: the app's log files (behaviors 5–8), on the desktop.
   5. **Defaults for every user**: read only, where an administrator puts an `appsettings.json` (F4.15 behavior 13).
2. A folder moved by configuration (`Engine:SettingsFolder`, `Engine:DataFolder`, `Tiles:CacheFolder`) shows the path in
   use and says "set in configuration". A folder that doesn't exist yet (no captures made, no defaults installed) is
   listed with "not created yet".
3. **Copy** puts the path on the clipboard, exactly as the system writes it, and says "Copied" for a moment. Each button
   has its own accessible name ("Copy the settings folder"). Where there's no clipboard (a browser off HTTPS or
   localhost) the buttons are hidden and the paths stay selectable, as the passcode calculator's number does (F0.5
   behavior 27.5).
4. Paths are shown in a monospace font, wrap at 200 % text, and are never shortened with an ellipsis.

### The log file (desktop)

5. The desktop app writes its log to files in a **`logs` folder in the Data folder** (maintainer, 2026-10-19), as well
   as to the terminal: `aprsmap.log` (from `Brand.Slug`), the newest, then `aprsmap.1.log` and so on.
6. **At most 5 files of 2 MB each**: when the newest reaches 2 MB, the files are renamed one place along and the oldest
   is deleted, so the logs never use more than 10 MB.
7. The level is the configured one (`Logging:LogLevel`, Information by default); the file has a line for each entry, with
   its UTC time, level, category and message, and the exception when there is one.
8. **Nothing secret is logged**, here or anywhere: no passcodes, operator passwords or session cookies. Messages'
   texts are logged at Debug only. The log stays on the computer; the app never sends it anywhere.

### On a gateway

9. **Only a signed-in operator** sees the server's folders (maintainer, 2026-10-19), with Copy. A viewer, and an
   operator not signed in, see instead: "This browser keeps your layout and appearance in its own storage", and no
   server path.
10. The gateway writes no log file: its log is the container's output (`docker logs`), and About says so to the
    operator.

## Service surface

- `StorageFolder(StorageFolderKind Kind, string Path, bool Configured, bool Exists)`; `StorageFolderKind`: `Settings`,
  `Data`, `Tiles`, `Logs`, `Machine`.
- `Task<IReadOnlyList<StorageFolder>> GetStorageFoldersAsync()`: operator-only on a gateway (`gateway.operator-only`),
  so the paths never reach a viewer's browser.
- Each part of the app reports its own folder: the engine its settings, data and machine folders (`AppFolders`,
  `SettingsLocation`); the tile service its cache (`IStorageFolderSource`, registered by `AddAprsMapTiles`); the desktop
  host its logs. The engine collects them, so the UI asks one call and `AprsMap.Core` needn't know about tiles.
- A file logger provider in `AprsMap.Core` (MIT; `ILoggerProvider`, `TimeProvider` for the time, the rolling of
  behavior 6), added by the desktop host only.
- In the UI, the About dialog's view model gains the folders and Copy, using the same clipboard function as the passcode
  calculator.

## APRS.NET dependencies

None: these are the app's own files.

## Desktop vs web differences

| | Desktop | Web (gateway) |
| --- | --- | --- |
| Folders shown | Settings, Data, Map tiles, Logs, Defaults for every user | The server's, to a signed-in operator only |
| Viewers | — | "This browser keeps your layout and appearance in its own storage" |
| Log | Rolling files in Data/logs, and the terminal | The container's output (`docker logs`) |
| Copy | The system clipboard | The browser's, on HTTPS or localhost |

## Acceptance tests

1. On Linux with no configuration, About lists `~/.config/aprsnet/aprsmap`, `~/.local/share/aprsnet/aprsmap`, the tile
   cache, `~/.local/share/aprsnet/aprsmap/logs` and `/etc/xdg/aprsnet/aprsmap` (not created yet), each with Copy; with
   `Engine:SettingsFolder` set, Settings shows that path and "set in configuration".
2. Copy puts exactly the path on the clipboard; without a clipboard the button is hidden and the path selectable.
3. The file logger writes lines with the UTC time, level, category and message; at 2 MB it rolls, keeping five files and
   deleting the sixth (with a small cap in the test).
4. A passcode, an operator password and a session cookie never appear in the log, at any level.
5. On a gateway, `GetStorageFoldersAsync` is refused for a viewer with `gateway.operator-only`, and the viewer's About
   shows the browser note and no path; a signed-in operator sees the folders.
6. About fits at 200 % text, in every palette, with the longest path wrapping.

## Decisions

Agreed with the maintainer (2026-10-19):

1. **Folders only**, not the files in them: folders are what people open and back up, and they stay the same between
   versions while the files inside change.
2. **A rolling log file on the desktop**, in Data/logs, listed in About, so there's a log to send however the app was
   started.
3. **On a gateway, only a signed-in operator sees the server's folders**; viewers are told their layout is kept in
   their browser.

For review:

4. **Our own small file logger** (proposed), rather than a logging package such as Serilog: one provider, rolling by
   size, about a hundred lines, and no new dependency for the MIT engine.
5. **5 files of 2 MB** (proposed): days of normal use at Information, small enough to attach to an issue.
6. **Open folder** on the desktop is left for later (proposed), so this stays to showing and copying.
