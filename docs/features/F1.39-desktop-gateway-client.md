# F1.39 The desktop app as a gateway client

Status: scoped for 0.8.0 ([#400](https://github.com/APRS-NET/AprsMap/issues/400), maintainer request, 2026-10-26); decisions proposed.

## User story

As an operator whose station runs as a gateway service (F1.37), I use the desktop app on that PC, or on another, as a
window onto the gateway: it shows the gateway's sources, stations, packets and dashboard, processed once by the
gateway, not again. Without the API key it only watches; with it, I use the gateway as if it were the app's own,
transmitting and changing settings.

## Background: what already exists

- The UI talks to the engine only through `IEngineService` (F0.4). The desktop app hosts its own engine in process; the
  browser app reaches a gateway's engine over SignalR with `RemoteEngineService` (AprsMap.Client.Remote).
- The gateway's operator port and the API key (F1.26, F1.38).

## Behavior

1. **Settings › Connection** on the desktop: **This computer** (the app's own engine, the default) or **A gateway**,
   with the gateway's address (`http://127.0.0.1:8081/` by default, its admin port on this PC) and the **API key**
   field (paste, show or hide). **Apply and restart** saves the choice and restarts the app into it (one Apply, as in
   Gateway access, maintainer 2026-10-26); choosing This computer and applying goes back, keeping the key for next
   time. `--gateway URL` on the command line does the same for one run, with the saved key.
   **Test** (#419, maintainer 2026-10-26) checks the address and key first, saving nothing: a gateway's
   `GET /auth/test` answers with its product, build version, contract version and what it makes of the key (accepted,
   refused, needs HTTPS, not the admin port, or none sent). Apply and restart is enabled only after a test passes for
   exactly what's in the fields. Nothing answering, something other than a gateway, another contract version, or a
   key the gateway won't take stops it, with the reason; no key passes, to watch only; another major.minor version
   passes with a warning that some features may be missing on one side.
2. **As a gateway client the app runs no engine of its own**: no APRS-IS or TNC connection, no GPS, no beacons, no
   history. Everything shown is the gateway's: its sources in the source pills and on the dashboard, its stations, its
   packets, its messages. Nothing is received or processed twice.
3. **Without the key, or with one the gateway refuses, it's read-only**, as a browser viewer is: settings show but
   can't be changed, sources and Transmit can't be switched, nothing can be sent. Settings › Connection says it's
   watching the gateway, and a refused key says why. The status bar says it too (#428): **Viewing pi.local:8081**, or
   **pi.local:8081 · operator** with the key, in the warning colour when the gateway refused the key, with the reason in
   its tooltip; clicking it opens Settings › Connection. Signing in with a
   password isn't offered: the app's hub connection carries the key, not a browser's session.
4. **With the key it's the gateway's operator** (F1.38): it transmits (when the gateway's Transmit is on) and changes
   settings, sources and toggles, exactly as the app does for its own engine.
5. **What stays the desktop's own**: appearance, layout, its preferences, and the update checks for the desktop app
   itself, which a local engine runs with nothing else started (`Engine:UpdatesOnly`). Map tiles come through the
   gateway's tile cache. The web viewer (F1.35) is off as a client, since the gateway already serves browsers, and
   Help › About's Open folder is gone, since the gateway's folders are on its own computer.
6. **The connection**: lost, the app says so and reconnects with backoff, as the browser app does; a gateway too old or
   too new for the app says so (F1.14 behavior 8).
7. **The key is kept in the desktop's settings folder**, in `gateway-client.json`, readable only by the user (mode 600
   on Linux and macOS).
8. **The gateway's version shows** (maintainer, 2026-10-27, #453): Help › About names it in place of the engine's
   ("Gateway 0.8.0-alpha.2 (Linux service) · APRS.NET …", with "container" or "run by hand" as the gateway reports),
   and so does the status bar's gateway tip. When its major.minor differs from the app's, both say so in the
   connection test's words (#419). The browser's About does the same, and viewers see it too: the connection test
   already gives the version without a key. `EngineStatus.Install` carries how the engine is installed.

## Service surface

None new on `IEngineService`. Desktop: `GatewayClientSettings(Uri? Gateway, string? ApiKey)`; `--gateway`.

## APRS.NET dependencies

None.

## Desktop vs web differences

Desktop only; the browser app is always a gateway client.

## Acceptance tests

1. Connected to a gateway (an in-memory one in tests), the desktop's main view shows the gateway's sources and
   stations, and the desktop runs no engine.
2. Without a key, saving settings and sending are refused and the UI shows the station read-only; with the key, both
   work.
3. Switching back to This computer restarts with the local engine and its own settings untouched.
4. The key file is mode 600.

## Decisions for review

1. **A restart to switch** (proposed): the app is built around one engine; switching live can come later.
2. **The desktop's own updates are still checked** (proposed), by the desktop, not taken from the gateway's.
3. **No web viewer as a client** (proposed).
