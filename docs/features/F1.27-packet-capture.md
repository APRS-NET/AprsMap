# F1.27 Packet capture for analysis

Status: spec'd for 0.5.0 ([#233](https://github.com/APRS-NET/AprsMap/issues/233); maintainer request, 2026-10-17).
The anonymized export waits on G31.

## User story

As an operator, I can leave the app recording the packets it couldn't make sense of, look through them later, and hand
the developer a file that goes straight into APRS.NET's test corpus, so formats seen in the wild get decoded and stay
decoded.

## Background: what already exists

- F1.8: the Packets panel's **Issues only** filter, and **Save** as a text log of `<UTC time> <raw line>`. It only
  writes the packets the list holds (at most 5,000, gone on restart), and as UTF-8.
- F1.20: track anomalies (repeated position, impossible speed and the rest), counted per station.
- APRS.NET: `AprsPacket.Issues` (`ParseIssueCode`), `ParseOutcome.Unsupported` and `PacketType.Unknown`. Its test
  corpus (`tests/corpus`) takes one packet per line, `<UTC receive timestamp> <raw APRS-IS line>`, in Latin-1 so
  every byte round-trips, and only after its anonymizer has replaced callsigns, names and e-mail addresses; a test
  fails on a raw capture.

## Behavior

### What's captured

1. A packet is **captured** when APRS.NET:
   1. reported parse issues for it (`Issues`), or
   2. didn't decode its data type (`ParseOutcome.Unsupported`, `PacketType.Unknown`, a raw NMEA `$` sentence), or
   3. decoded it but marked part of it as unrecognised (G31: an unknown extension, an odd path element, data left over
      after the comment's known fields).
   Track anomalies (F1.20) are about a station, not a format, and aren't captured.
2. Each captured line keeps the raw packet **byte for byte** (Latin-1, as received, from APRS-IS or after the KISS
   frame is turned into text), the UTC time it arrived, the source it came on, and why it was captured (the issue
   codes, or `unsupported` / `unknown-type` / G31's codes).
3. **Repeats are left out**: a packet whose station, reason and data type were captured in the last hour is counted,
   not written again, so one misconfigured tracker doesn't fill the file.

### Recording

4. **Capture unexpected packets** is a switch in Settings › Data, **off by default**. While on, captured packets go to
   `capture/` in the settings folder: one file a day, `YYYY-MM-DD.log`, in the corpus line format, with the reasons in
   a `.json` beside it so the log stays a plain corpus file.
5. **Limits**: 50 MB in all and 30 days by default, both settable; the oldest day goes first. Recording never slows
   receiving: lines are queued and written in the background, and dropped (counted) if the disk can't keep up.
6. While recording, the status bar's sources menu says so ("Capturing unexpected packets: 37 today").

### Looking through them

7. A **Captured packets** panel (a dockable panel, F1.0) lists them newest first, with the time, source, station,
   reasons in words (F1.8's issue text) and the raw line; filters by reason and by day; a row expands to the raw text
   with the part at fault marked, as F1.8 does. **Open in Packets** shows that station's packets in F1.8.

### Handing them to the developer

8. **Export for analysis** (in the panel, for the rows shown or chosen) writes one file ready for `tests/corpus/`:
   1. **Anonymized** (the default, needs G31): callsigns, station names and e-mail addresses replaced the way APRS.NET's
      corpus tool does it, every line the same length as before, positions, TOCALLs, Mic-E destinations and path
      aliases kept. The key that undoes it is never written into the export.
   2. **As received**: the raw lines, with a note that it can't go into the corpus until anonymized.
   With it goes a short note (Markdown): the app's name and version (`Brand.*`), APRS.NET's version, the date range,
   and a count per reason, so it can go into an APRS.NET issue as it is.
9. **Report on GitHub** opens the browser at a new APRS.NET issue with the note filled in, for the viewer to attach the
   export and submit. Nothing is ever sent by the app itself.
10. **Clear captured** deletes the files (F1.19's housekeeping lists it too).

### On a gateway

11. Capture is the station operator's: the switch, the panel and Export are operator-only (`gateway.operator-only`,
    until F2.9), and the files live in the gateway's `/data`. A viewer sees neither.

## Service surface

- `IEngineService`:
  - `GetCaptureAsync(CaptureQuery)` → `CapturedPacket` list (time, source id, raw, station, reasons) and the per-day
    counts;
  - `ExportCaptureAsync(CaptureExport)` → the export's text and note (anonymized or as received), written by the view
    to a place the viewer picks (desktop: a save dialog; web: a download);
  - `ClearCaptureAsync()`.
- `AppSettings` gains `Capture` (`On`, `MaxMegabytes`, `Days`).
- `EngineStatus` gains `CapturedToday`.
- Error codes: `capture.not-available` (anonymizing before G31), `capture.write-failed`.

## APRS.NET dependencies

- **G31** (corpus capture helpers, [APRS.NET#236](https://github.com/APRS-NET/APRS.NET/issues/236)): the anonymizer as a library API rather than a script, the corpus line format
  (write and read, Latin-1), and a list of the unrecognised parts of a decoded packet. Without it, behaviors 1.3 and
  8.1 wait; the rest builds on what's delivered.

## Desktop vs web differences

| | Desktop | Web (gateway) |
| --- | --- | --- |
| Who | The user | The operator only, after F2.9 |
| Files | `capture/` in the settings folder | `capture/` in `/data` |
| Export | Save dialog | Download |

## Acceptance tests

1. With capture on, a corpus line with a bad latitude, one with an unsupported data type and a good position arrive: the
   first two are written, with their reasons; the good one isn't.
2. A Mic-E packet whose bytes aren't valid UTF-8 is written and read back byte for byte.
3. The same tracker's bad packet arriving 100 times in an hour is written once and counted 100 times.
4. The files stay under the size limit, the oldest day going first, and nothing is written while capture is off.
5. The anonymized export passes APRS.NET's corpus file checks (format, timestamps in order, no real callsigns), each
   line as long as the original; the note names both versions and counts each reason.
6. Report on GitHub opens a URL on APRS.NET's new-issue page with the note, and nothing is uploaded.
7. On a gateway, every capture call is refused with `gateway.operator-only`.

## Decisions for review

1. **Off by default** (proposed): it writes files, so the operator turns it on.
2. **One line per station, reason and type an hour** (proposed), counting the rest.
3. **Anonymized by default** (proposed), with "as received" available and marked as not for the corpus.
4. **Track anomalies aren't captured** (proposed): they're a station's behaviour, not a format to decode.
5. **The app never uploads** (proposed): Report on GitHub only opens the browser.
6. **50 MB and 30 days** (proposed) as the default limits.
