# F2.8 Answering queries

Status: built for 0.6.0 ([#200](https://github.com/APRS-NET/AprsMap/issues/200)) except `?APRSH`, `?APRSM`, `?IGATE?`
and `?WX?` (behavior 6); decisions proposed 2026-10-21 for the maintainer's review. In the UI: Settings › Messaging ›
Answer APRS queries.

## User story

As an operator, when another station asks mine where it is, what its status is, or what it hears, my station answers as
APRS stations are expected to, without my doing anything, and only in the ways I've allowed it to transmit.

## Background: what already exists

- APRS.NET 0.4.0-alpha.12's `QueryResponder` (G19): it recognises the general queries every station hears (`?APRS?`,
  `?IGATE?`, `?WX?`) and the queries directed at a station (`?APRSP`, `?APRSS`, `?APRSD`, `?APRSH`, `?APRSM`, `?APRSO`,
  `?APRST` and `?PING?`) (APRS101 chapter 15), answers a general query only after a random wait (2 to 60 s) and only when
  its footprint includes the station, answers the same query from the same station once in 2 minutes, and gives the
  payloads to send.
- Every send follows F2.1: Transmit on, a licensed profile, a source that isn't RX only and is switched on.

## Behavior

1. **Answer APRS queries** is a switch in Settings › Messaging, per profile, **on by default** (proposed): answering
   queries is what APRS expects of a station, and nothing is sent unless Transmit is on and the profile may send.
2. **Not before the position is confirmed** (F2.1 behavior 12): until a position has been sent by hand once, nothing
   automatic goes out, answers included.
3. **What it answers with**:
   1. `?APRSP`, and `?APRS?` with the status: the position as a beacon sends it (F2.2), where the GPS says while its fix
      is fresh (F3.6), with its course and speed;
   2. `?APRSS`: the status (F2.2, F2.11), when the profile has one;
   3. `?APRSO`: the profile's live objects and items (F2.7);
   4. `?APRSD`: the stations this station's own receivers heard direct in the last hour, the most recent first;
   5. `?APRST` and `?PING?`: the path the query came by, as APRS.NET words it.
4. **Back the way it came**: each answer goes on the source the query was heard on, after the responder's wait, and
   only if that source can send then; otherwise it's dropped and the log says so (F1.32, Transmit area).
5. Each answer is logged: which query, from whom, on which source.
6. **Not answered yet** (proposed: later): `?APRSH` (how often a station was heard, hour by hour: the station store keeps
   no hourly counts), `?APRSM` (sending waiting messages again, with F2.4), `?IGATE?` (with the IGate, F3.4) and `?WX?`
   (with a weather station of the app's own).
7. A query addressed to the station is read as a query, not a message (APRS.NET parses `:CALL     :?APRSP` as one), so
   it doesn't show in Messages and auto-reply (F2.10) never sees it; the packet list shows it, and the log its answer.

## Service surface

- `StationProfile.AnswerQueries` (`bool?`, null for on).
- No new `IEngineService` member.

## Acceptance tests

1. `?APRSP` on the TNC is answered on the TNC with the position; `?APRSS` with the status.
2. `?APRS?` is answered after a wait between 2 and 60 s; the same query again within 2 minutes isn't.
3. `?APRSD` lists the stations heard direct; `?APRSO` the live objects.
4. Nothing is answered with the switch off, Transmit off, or the position not yet confirmed.
5. A query doesn't show in Messages, and auto-reply doesn't answer it.

## Decisions for review

All proposed (2026-10-21), built as described so they can be tried:

1. **On by default**, per profile, under every transmit rule.
2. **Not before the position is confirmed.**
3. **Answers go back on the source the query came from.**
4. **`?APRSH`, `?APRSM`, `?IGATE?` and `?WX?` later.**
5. **Directed queries don't show in Messages**: they're queries, not conversation (as APRS.NET reads them).
