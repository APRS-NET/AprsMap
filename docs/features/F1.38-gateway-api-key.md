# F1.38 Gateway API key

Status: scoped for 0.8.0 ([#399](https://github.com/APRS-NET/AprsMap/issues/399), maintainer request, 2026-10-26); decisions 1 and 2 by the maintainer, the rest proposed.

## User story

As the gateway's operator, I generate an API key in the admin web app, copy it, and paste it into the desktop app I
connect to the gateway with (F1.39). With the key, that app controls the gateway as if it were its own: it transmits,
and it changes the station's settings. Without it, an app only watches.

## Background: what already exists

- Operators sign in with a password on the operator port (F2.9, F1.26); a signed-in browser may transmit and change
  settings. The viewer port never offers sign-in.
- Guessing is limited and logged (F2.9 behaviors 5, 6).

## Behavior

1. **Settings › Gateway access** in the admin web app, for a signed-in operator only: **Let apps in with an API key**
   (on or off), an **API key** field with **Generate** (a new random key, 32 bytes, written as 43 URL-safe characters)
   and **Copy**, and **Apply** (maintainer, 2026-10-26: one Apply, not Save and Remove). A key can also be typed or
   pasted, at least 32 characters. Applying a key replaces the old one at once: apps using it are disconnected and
   refused from their next call. Switched off and applied, the key is removed and API access is off.
2. **What the key allows** (maintainer, 2026-10-26): **everything a signed-in operator may**: transmitting (when the
   station's Transmit is on, F2.1) and changing settings, sources, toggles and profiles.
3. **Passwords stay** (maintainer, 2026-10-26): browsers keep signing in with operator passwords; the key is for apps.
4. **Only on the operator port**, as sign-in is (F1.26 behavior 3): a key sent to the viewer port is ignored, and that
   connection stays a viewer. An app reaches the operator port on the PC itself, or over the network when
   `operator_listen` allows it (F1.37).
5. **Sent as `Authorization: Bearer <key>`** on the hub's negotiate request and its connection; never in a URL, so it
   doesn't end up in logs or proxies. Over plain HTTP it's accepted only from loopback, as passwords are (F2.9
   behavior 8.1).
6. **Kept as a hash**, in `api-key.json` in the gateway's data folder: the key itself is shown only when generated,
   before it's saved. Afterwards the field says a key is set and when, and Copy is gone; generating a new one is how
   to see one again.
7. **Guessing is limited and logged** like sign-in: a wrong key counts as a failed attempt from that address (only the
   address, so guessing from one place can't lock the key out for everyone), and each accepted and refused key is in
   the operator audit log, without the key. `/auth/me` with the key says whether the gateway took it
   (`gateway.api-key-refused`), so an app can say why it's only watching.
8. **The status names it**: a connection let in by the key shows as the operator "API key" wherever signed-in operators
   are listed.

## Service surface

- `IEngineService.GetApiKeyStatusAsync` (set or not, and when), `GenerateApiKeyAsync` (returns a new key, unsaved),
  `SaveApiKeyAsync(key)`, `RemoveApiKeyAsync`: operator only, on the gateway; the desktop's in-process engine answers
  that there's no gateway access to set (`gateway.api-key-not-here`).
- `RemoteEngineService.Create(uri, apiKey)`: sends the key with every connection.
- Error codes `gateway.api-key-refused` and `gateway.api-key-too-short`.

## APRS.NET dependencies

None.

## Desktop vs web differences

Set on the gateway's admin web app; used by the desktop app as a gateway client (F1.39).

## Acceptance tests

1. A generated key is 43 URL-safe characters; saved, it's stored as a hash and the field no longer shows it.
2. A hub connection on the operator port with the key may change settings and transmit; without it, or with a wrong
   one, it's a viewer; on the viewer port, the key changes nothing.
3. After a new key is saved, a connection with the old one is refused at its next call.
4. Wrong keys are rate-limited and logged, the key never in the log.

## Decisions for review

1. **The key allows everything an operator may** (maintainer, 2026-10-26).
2. **Passwords stay for browsers** (maintainer, 2026-10-26).
3. **One key** (proposed); several named keys, each revocable, can follow.
4. **Only on the operator port** (proposed), so the public port stays read-only whatever an app sends.
5. **Stored as a hash, shown once** (proposed): the same salted PBKDF2 hash as operator passwords, checked once per
   connection.
6. **An app with the key may also change the key** (as built), since it may do everything an operator may; a
   password-only rule for Gateway access can follow if wanted.
