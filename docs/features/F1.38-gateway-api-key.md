# F1.38 Gateway API key

Status: scoped for 0.8.0 ([#399](https://github.com/APRS-NET/zedMap/issues/399), maintainer request, 2026-10-26); per-app keys 2026-11-15. Decisions 1–3 by the maintainer, the rest proposed.

## User story

As the gateway's operator, I add an app in the admin web app, name it ("Derek's laptop"), copy its new key, and paste
it into the desktop app I connect to the gateway with (F1.39). With the key, that app controls the gateway as if it
were its own: it transmits, and it changes the station's settings. Without it, an app only watches. Each app has its
own key, so letting a new device in, or shutting a lost one out, leaves the others working (maintainer, 2026-11-15).

## Background: what already exists

- Operators sign in with a password on the operator port (F2.9, F1.26); a signed-in browser may transmit and change
  settings. The viewer port never offers sign-in.
- Guessing is limited and logged (F2.9 behaviors 5, 6).

## Behavior

1. **Settings › Gateway access** in the admin web app, for a signed-in operator only, lists the apps with a key, each with
   **Revoke**. **Add an app** takes a name (up to 40 characters, unique, ignoring case) and what it may do, and
   **Create key** makes a new random key, 32 bytes, written as 43 URL-safe characters (maintainer, 2026-11-15: one key
   per app, shown once at creation, revocable one at a time). Revoking a key disconnects its app at once and refuses it
   from then on; the other apps' keys go on working. While a key's app is connected, the first Revoke only says so; a
   second goes ahead (#450). A gateway keeps at most 50 keys.
2. **What a key allows** is chosen per key: **Operator**, everything a signed-in operator may (transmitting when the
   station's Transmit is on, F2.1, and changing settings, sources, toggles and profiles; maintainer, 2026-10-26), or
   **Watch only**, as a viewer, for a kiosk or a wall display that should still be named and revocable.
3. **Passwords stay** (maintainer, 2026-10-26): browsers keep signing in with operator passwords; keys are for apps.
4. **Only on the operator port**, as sign-in is (F1.26 behavior 3): a key sent to the viewer port is ignored, and that
   connection stays a viewer. An app reaches the operator port on the PC itself, or over the network when
   `operator_listen` allows it (F1.37).
5. **Sent as `Authorization: Bearer <key>`** on the hub's negotiate request and its connection; never in a URL, so it
   doesn't end up in logs or proxies. Over plain HTTP it's accepted only from loopback, as passwords are (F2.9
   behavior 8.1).
6. **Kept as a hash**, in `api-keys.json` in the gateway's data folder, readable by the gateway's user only: the key
   itself is shown once, when it's created, with **Copy**, and not again. Lost, it's replaced by adding the app again
   and revoking the old key. **Check a key** tests a key an app has against the gateway's keys, saving nothing (#447).
7. **Guessing is limited and logged** like sign-in: a wrong key counts as a failed attempt from that address (only the
   address, so guessing from one place can't lock the keys out for everyone), and each accepted and refused key is in
   the operator audit log, by name, without the key. The same wrong key again from the same address counts once per
   15-minute window (#450): an app left with a revoked key sends it on every start and test, which isn't guessing, and
   shouldn't make its computer wait. `/auth/me` with the key says whether the gateway took it
   (`gateway.api-key-refused`), or, while the address waits, that it didn't check it (429 `auth.too-many-tries` with
   the minutes left); the connection test answers `Waiting` with the minutes. So an app can say why it's only
   watching, and a wait never reads as a wrong key.
8. **The status names it**: a connection let in by an operator key shows as the operator "API key: <name>" wherever
   signed-in operators are listed; `/auth/me` names a watch-only key's app too.
9. **Each key says when and where it was last used** (time and address) and how many connections it has now, so the
   operator can tell which key a device has and what revoking it disconnects. The last use is written to disk at most
   every 5 minutes per address.
10. **The single key of earlier versions is kept** as an operator key named "Existing key", so the apps using it keep
    working after the update; revoke it once they have keys of their own. `api-key.json` is renamed
    `api-key.json.moved`.

## Service surface

- `IEngineService.GetApiKeysAsync` (each key's name, access, created, last used, connections; never the key),
  `CreateApiKeyAsync(name, access)` (returns the key, this once), `RevokeApiKeyAsync(id)`, `CheckApiKeyAsync(key)`:
  operator only, on the gateway; the desktop's in-process engine answers that there are no keys to set
  (`gateway.api-key-not-here`).
- `RemoteEngineService.Create(uri, apiKey)`: sends the key with every connection.
- Error codes `gateway.api-key-refused`, `gateway.api-key-name` and `gateway.api-key-too-short`.

## APRS.NET dependencies

None.

## Desktop vs web differences

Set on the gateway's admin web app; used by the desktop app as a gateway client (F1.39).

## Acceptance tests

1. A new key is 43 URL-safe characters, shown once; it's stored as a hash, and the list never shows it.
2. A hub connection on the operator port with an operator key may change settings and transmit; with a watch-only key,
   none, or a wrong one, it's a viewer; on the viewer port, the key changes nothing.
3. Revoking one app's key disconnects that app and refuses its key; another app's key goes on working.
4. Wrong keys are rate-limited and logged, the key never in the log; one old key retried doesn't make its address wait.
5. A waiting address is told so, with the minutes left, by `/auth/me`, the connection test and the desktop's status.
6. Each key lists when and where it was last used and its connections; Revoke asks once more while its app is
   connected.
7. An earlier version's single key keeps working as "Existing key" until it's revoked.

## Decisions for review

1. **An operator key allows everything an operator may** (maintainer, 2026-10-26).
2. **Passwords stay for browsers** (maintainer, 2026-10-26).
3. **One key per app, shown once, revocable one at a time** (maintainer, 2026-11-15), replacing the single key: the
   operator couldn't see the key again to let a new device in, and replacing it broke every other app.
4. **Only on the operator port** (proposed), so the public port stays read-only whatever an app sends.
5. **Stored as a hash, shown once**: a SHA-256 of the 32 random bytes, which can't be reversed or guessed, so it's
   checked against every key at no real cost; the earlier single key keeps the salted PBKDF2 hash it was saved with.
6. **An app with an operator key may also manage keys** (as built), since it may do everything an operator may; a
   password-only rule for API keys can follow if wanted.
7. **A repeated wrong key counts once** (proposed, #450), by an in-memory SHA-256 fingerprint of the key per address:
   a guesser tries different keys, so this costs nothing against guessing. The wait still refuses even the right key,
   from that address, until it ends.
8. **Watch-only keys, and the last use with its address** (proposed, 2026-11-15; to confirm).
9. **The earlier key is kept as "Existing key"** (proposed, 2026-11-15; to confirm) rather than removed, so updating
   the gateway doesn't lock its apps out.
