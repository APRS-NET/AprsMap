# F2.10 Auto-reply

Status: built for 0.6.0 ([#202](https://github.com/APRS-NET/AprsMap/issues/202)); decisions proposed 2026-10-19 for the
maintainer's review. In the UI: Settings › Messaging › Auto-reply; in Messages, an auto-reply is marked Automatic reply.

## User story

As an operator who steps away from the station, I turn on an away message, and whoever messages me gets it once, after
a short wait in case I'm there to answer myself, the same way their message came. Nobody gets it twice in an hour,
services and automatic messages never get it, and nothing goes out while I'm actually using the station.

## Background: what already exists

- Messaging (F2.4): conversations, acks and retries, every send following F2.1's rules.
- Ping (F2.13): a pong goes back the way the ping came, marked Automatic reply, at most one an interval for the whole
  station. Auto-reply uses the same route back and the same marking.
- Observed in APRSIS32 (docs/reference/observation-2026-10-13.md): an auto-reply text, sent "only when inactive for N"
  and "no more than once per N". This design is the app's own.

## Behavior

### Turning it on

1. **Auto-reply** is a switch in Settings › Messaging, per profile, **off** by default (proposed): it transmits by
   itself, so the operator chooses it, as with ping.
2. **The text**: 1 to 67 characters, one message, F2.4's message rules (printable ASCII, no `|`, `~` or `{`). Default:
   "I'm away from the station and will reply when I'm back." (proposed).
3. Every rule a message follows applies (F2.1): a licensed profile, the Transmit switch on, and the source not RX only
   and switched on. While any of them stops it, nothing is sent and the reason is logged (F1.32, Messages area).

### When it answers

4. **Only when away** (proposed): when no message has been sent by hand from this station for **N minutes**, 15 by
   default (0 to 1440; 0 means always). "By hand" means written in Messages; automatic ones don't count. The engine
   knows it on the desktop and on a gateway alike, without the UI reporting input.
5. **Once per correspondent** per **M minutes**, 60 by default (1 to 1440) (proposed): a second message from the same
   station within that time gets no reply.
6. **After a delay**, 30 seconds by default (0 to 600) (proposed): the reply waits, and is cancelled if the operator
   sends that station a message by hand meanwhile, so someone who is there answers in person.
7. **Never to**:
   1. a ping (F2.13 answers it) or a message starting with the ping's pong phrase;
   2. a message that is itself an auto-reply (it starts with this profile's auto-reply text), so two stations with
      auto-reply on don't answer each other more than once (behavior 5 limits it too);
   3. bulletins, announcements, group and NWS messages, which aren't addressed to the station;
   4. known service addresses: `ANSRVR`, `CQSRVR`, `EMAIL`, `EMAIL-2`, `WLNK-1`, `SMSGTE`, `WXBOT`, `WXSVR`, `REPEAT`,
      `FINDU`, `IGATE`, `QRU` (proposed list; any SSID of these), which answer by themselves.
8. **Back the way it came**, as a pong (F2.13 behavior 9): the source the message arrived on, with its TX path on RF. It
   is a message with an ID, acked and retried.

### Seen in the app

9. The auto-reply shows in the conversation marked **Automatic reply** (as a pong); the received message counts as
   unread as usual: the operator still reads it when back.
10. The log has a line for each auto-reply sent, and for each one held back with why (away time, once per, a service,
    Transmit off).

## Service surface

- `AutoReplySettings(bool On = false, string? Text = null, int AwayMinutes = 15, int OncePerMinutes = 60,
  int DelaySeconds = 30)` on `StationProfile` (`AutoReply`); a null text means the default of behavior 2.
- Error codes: `settings.auto-reply.text-invalid`, `settings.auto-reply.limit-invalid`.
- The messenger (F2.4) sends it; no new `IEngineService` member beyond the settings.

## APRS.NET dependencies

None beyond G10 (messaging, delivered).

## Desktop vs web differences

| | Desktop | Web (gateway) |
| --- | --- | --- |
| Turning it on, text, timings | The user | The operator (F2.9) |
| Away | No message sent by hand from this app | No message sent by hand from any browser |

## Acceptance tests

1. Off (the default), a message gets no reply.
2. On, with nothing sent by hand for 15 minutes (a fake clock), a message from NZ0P-9 on the TNC gets the text on the
   TNC after 30 seconds, marked automatic; the received message is unread.
3. A second message from NZ0P-9 within 60 minutes gets none; one from another station does.
4. Having sent a message by hand 5 minutes ago, no reply goes out.
5. A reply waiting its 30 seconds is cancelled when the operator messages that station.
6. No reply to ANSRVR, EMAIL-2, a ping, a pong, or a message starting with the auto-reply text.
7. With Transmit off, nothing is sent and the log says why.
8. A text over 67 characters or with `{`, and limits out of range, are refused.

## Decisions for review

All proposed (2026-10-19), built as described so they can be tried:

1. **Off by default**, per profile, in Settings › Messaging.
2. **Away is the engine's measure**: no message sent by hand for N minutes (15), rather than mouse and keyboard
   activity, which a gateway can't see and would need the UI to report.
3. **Once per correspondent per 60 minutes**, as the observed "no more than once per N".
4. **A 30-second delay**, cancelled by a reply by hand.
5. **The list of service addresses** in behavior 7.4, and replies only to messages addressed to the station.
6. **Back the way it came**, as ping, rather than by the conversation's Send via.
