# F1.9 View filters

Status: draft

## User story

As an operator, I can choose which stations the map and the station list show, without changing what APRS-IS sends:
only weather stations during a storm, only stations heard on RF when I'm checking my local network, only those that
can take messages, or only a certain kind of device or tag. I can switch quickly between showing everything and my
usual selection.

## Behavior

### What can be filtered

1. A **View** filter is a set of conditions; a station is shown when it matches all of them:
   1. **Kind**: stations, objects, items (F1.3);
   2. **Category** of its symbol (APRS.NET `AprsSymbolCategory`: vehicles, aircraft, weather, emergency, buildings and
      so on), and individual symbols;
   3. **Heard**: last heard within 10 min, 30 min, 1 h or 2 h;
   4. **Reception** (G20): RF direct, RF via digipeaters, RF anywhere, APRS-IS only;
   5. **Capability**: message-capable (from the position's messaging flag), with weather (F1.10), with telemetry
      (F1.11), with a track (F1.5);
   6. **Device** (G07): by vendor or class (tracker, rig, software, digipeater), listed with counts of what is heard;
   7. **Mic-E status** (en route, in service, emergency and so on);
   8. **Tags**: `!word!` and `#word` tags found in comments and status texts, listed with counts as they are heard.
2. Lists (devices, tags, symbols) show only values heard, with counts, so they never show empty choices.
3. **Emergency** stations (Mic-E emergency, or the emergency symbol) are always shown, whatever the filter, and the
   filter's chip says so.

### Using it

4. A **Filter** button on the map opens a panel with the conditions; the panel and the map update together. An active
   filter shows a chip ("Filtered · 312 of 2,140 · Clear"), so the map never looks empty without a reason.
5. **All** and **My filter**: one switch between showing everything and the last filter used, so a viewer can check
   what they're missing without losing their selection.
6. The filter applies to the map and the station list (F1.7), not to the packet list, which has its own (F1.8), and
   not to what the server sends (F1.2).
7. The filter is a **per-viewer** preference: each browser on a gateway has its own, kept across sessions
   (`IPreferenceStore`, F0.6).

## Service surface

- `StationFilter` (contract record) with the conditions above; `WatchStationsAsync(StationFilter? filter)` and
  `QueryStationsAsync` (F1.7) take it. The engine applies it per subscription, so a browser receives only what it shows.
  Changing it restarts the stream with a snapshot.
- New `Task<ViewFacets> GetViewFacetsAsync()`: the heard values with counts (devices, tags, symbols, categories) for
  behavior 2.
- The station entry (F1.3) gains the fields the filter needs: messaging flag, Mic-E status, tags, reception, device.
  Tags are found by the engine when a comment or status changes.

## APRS.NET dependencies

- **G20** for reception, **G07** for devices: delivered (`0.2.0-alpha.2`, `PathAnalysis` and `AprsNet.DeviceId`).
- Symbol categories (`AprsSymbolCategory`), the messaging flag (`IsMessagingCapable`) and Mic-E status (`MicEMessage`):
  delivered.
- Tag extraction is plain text matching of comments, not APRS protocol analysis, so it lives in the engine.

## Desktop vs web differences

None: each viewer has their own filter on both.

## Acceptance tests

1. Each condition shows and hides the right stations from a scripted store; conditions combine with AND.
2. Facet lists show heard values with counts and update as stations arrive.
3. Emergency stations show through any filter.
4. The chip shows the counts; All and My filter switch without losing the selection.
5. Two browsers on one gateway keep different filters; each receives only its matches.
6. The panel works from the keyboard and at 200 % text in every palette.

## Decisions for review

1. **Emergencies always shown** (behavior 3). Proposed: yes.
2. **Filtering in the engine per subscription** (proposed), against filtering in the UI: it saves browser bandwidth at
   some engine cost per viewer.
3. **Tag extraction in AprsMap** (proposed): `!word!` and `#word` are user conventions in free text, not APRS
   protocol, so they don't need an APRS.NET gap. If the maintainer prefers them in APRS.NET, they become a new gap.
