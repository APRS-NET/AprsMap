# F1.7 Station list

Status: draft

## User story

As an operator, I see every station I'm hearing as a list I can search and sort: nearest first, most recent first or
by name. I find a station by typing part of its callsign, jump to it on the map, or follow it so the map keeps it in
view as it moves. The list is also how I reach stations with a keyboard or screen reader.

## Behavior

### The list

1. A **Stations** list in the shell (UX doc: a rail destination on a wide window, a sheet on a narrow one) with a row
   per entry in the store (F1.3): symbol, name, last heard (relative), distance and bearing from me (F1.13), and the
   comment's start. Stale entries are greyed.
2. **Sort**: Last heard (default, newest first) · Name · Distance (nearest first; entries without a position last).
   The choice is a per-viewer preference.
3. **Search**: a box above the list matches the start of the name or any part of it, case-insensitive (`W1A` finds
   `W1AW-9`; `-9` finds every SSID 9). `/` or Ctrl+F focuses it from the map.
4. **Kinds**: All · Stations · Objects and items.
5. The list updates live from the engine, but rows don't jump under the pointer: while the pointer or keyboard focus is
   in the list, re-sorting waits until it leaves (new entries still appear).
6. Lists of 50,000 entries stay responsive: the engine sorts and filters, and the UI fetches pages as the list scrolls
   (virtualized rows).

### Acting on a station

7. Selecting a row selects the station on the map and opens its details (F1.6). **Enter** or double-click **centres**
   the map on it.
8. **Follow** (from a row's menu, the details pane, or `L` with a station selected): the map keeps the station centred
   as it moves, with a "Following *name*" chip on the map; panning by hand, Escape or the chip's close stops it. The
   followed station's track uses the followed style (F1.5), and its friend range joins the filter (F1.2).
9. **Go to** (`G`): the map re-centres on the most recently selected station, or on my location when none is selected.

## Service surface

- New `Task<StationPage> QueryStationsAsync(StationQuery query)`: search text, kind, sort, offset and count; returns
  rows (name, kind, symbol, last heard, stale, distance and bearing, comment start) and the total. Sorting and search
  run in the engine, so a browser never downloads the whole store.
- The list refreshes from the station stream (F0.2): a batch of changes triggers a re-query of the visible page,
  throttled to once a second.
- Following is UI state (per viewer), reported to the engine for the filter (F1.2's `SetMapViewAsync` gains the
  followed station's name).

## APRS.NET dependencies

- **G08**: distance and bearing, and the distance sort (via F1.13): delivered (`0.2.0-alpha.2`, `Geodesy`).

## Desktop vs web differences

None, except that on a gateway following doesn't change the station's filter unless `Gateway:FollowViewers` is on
(F1.2).

## Acceptance tests

1. Each sort orders rows as described; distance puts unknown positions last.
2. Search matches start and substring, case-insensitive; kind filters combine with search.
3. A query over 50,000 entries returns a page in under 50 ms (engine benchmark).
4. Rows don't re-sort while the pointer is in the list; new entries still appear.
5. Follow keeps a moving station centred; a manual pan stops it; Go to falls back to my location.
6. Keyboard: Tab to the search, arrows through rows, Enter centres, the details open; the list announces its row count
   to screen readers.

## Decisions for review

1. **Default sort**: Last heard (proposed) or Distance? Last heard works without a location or G08.
2. **Holding the sort while pointing** (behavior 5). Proposed: yes; the alternative is a manual Refresh.
