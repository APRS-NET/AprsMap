# F1.40 Update and restart the Linux service gateway from the admin web app

Status: scoped for 0.8.0 ([#407](https://github.com/APRS-NET/AprsMap/issues/407), maintainer request, 2026-10-26); decisions 1 and 2 by the maintainer, the rest proposed.

## User story

As the operator of a gateway installed as the Linux service (F1.37), I'm told in the admin web app that a new version
is out, and I press **Update and restart**: the gateway fetches the release, checks it, puts it in place and comes back
on the new version, with my configuration and station untouched. When something is stuck, I press **Restart**. I
never need a shell on the gateway's PC for either.

## Background: what already exists

- The update check (F4.15) runs in the engine on the gateway too; only the operator sees the notice (behavior 15). Its
  dialog has no install button on a gateway: it shows the image tag and the Docker commands to update (behavior 16).
  Readiness is the release's image marker (behavior 4.3).
- The Linux service (F1.37): the gateway runs as the unprivileged user `aprsmap` from `/opt/aprsmap-gateway` (owned by
  root, read-only to the service: `ProtectSystem=strict`), configured in `/etc/aprsmap/gateway.toml`, data in
  `/var/lib/aprsmap`, and `install.sh` installs or updates it from a release tarball. Each release attaches
  `aprsmap-gateway-vX-linux-x64.tar.gz` and `…-linux-arm64.tar.gz`.
- The operator: signed in with a password (F2.9), or an app with the API key (F1.38).

## Behavior

1. **Only the Linux service** (maintainer, 2026-10-26). The service's unit tells the gateway it's the service
   (`Engine__Updates__Kind=Service`); a gateway that isn't (the container, or the gateway run by hand) offers neither
   Update nor Restart. A container is restarted by the Docker engine (its restart policy, `docker compose restart`) and
   updated by pulling a new image, so its notice stays as it is (F4.15 behavior 16).
2. **Restart**, for the operator only: in Help › About on the service gateway, **Restart gateway**, after a
   confirmation ("Everyone watching is disconnected for a few seconds"). The gateway stops cleanly (sources closed,
   history and settings saved, as on a stop) and exits; systemd starts it again (`Restart=always`). Browsers and apps
   reconnect by themselves (F1.14 behavior 7, F1.39 behavior 6).
3. **Ready**, for the service: a release is ready when its tarball for this machine's architecture
   (`aprsmap-gateway-vX-linux-x64.tar.gz` or `…-linux-arm64.tar.gz`) and that tarball's checksum file (`….tar.gz.sha256`)
   are attached; the release workflow attaches the checksum beside each tarball. File names use `Brand.Slug`.
4. **Update and restart**: the service gateway's update dialog has the button (as the installed desktop's does, F4.15
   behavior 9.2), for the operator only. Pressed, after a confirmation:
   1. the gateway writes a request, `update-request.json` in its data folder, with the version only, and says
      **Updating to vX…** in the notice; it does nothing else itself, and never needs more rights than it has;
   2. systemd sees the request (a path unit, `aprsmap-gateway-update.path`) and starts the **updater**
      (`aprsmap-gateway-update.service`, as root, one shot), installed by `install.sh` as
      `/usr/local/libexec/aprsmap-gateway-update`, outside the folder it replaces;
   3. the updater reads the version (it must be a SemVer `vX` newer than the installed one; anything else is refused)
      and builds the download addresses itself, from the release address fixed at install and this machine's
      architecture: a request can't name a URL, a file or a command. The release workflow puts the release address and
      the version in each tarball (`release-source`, `version`);
   4. it downloads the tarball and its checksum over HTTPS, checks the SHA-256, unpacks it beside the installed one,
      keeps the installed one as `/opt/aprsmap-gateway.previous`, swaps the new one in, and restarts the service;
   5. if the new version doesn't stay running for 30 seconds without systemd restarting it, it puts the previous one
      back, restarts it, and records why (as built: the service's state and restart count, rather than `/healthz`,
      whose address is in the TOML file);
   6. it writes its progress and result to `update-status.json` in the data folder (downloading, checking,
      installing, restarting, done, or failed with the reason), and removes the request.
   The configuration, data, operators and API key are kept, as `install.sh` keeps them; the unit and the updater's own
   files are refreshed from the new release.
5. **The notice follows it**: while the update runs, the notice says which step it's on; after the restart the gateway
   shows **Updated to vX** once to the operator, or **The update to vX failed: <reason>; still on vY**, with the
   updater's log in the journal (`journalctl -u aprsmap-gateway-update`).
6. **Logged**: who asked for an update or a restart, and when, in the operator audit log (F2.9 behavior 15); the
   updater logs each step to the journal.
7. **One at a time**: while an update runs, Update and Restart aren't offered; a request older than 15 minutes that
   the updater never picked up is dropped, and the notice says the updater isn't installed or isn't running.

## Service surface

- `IEngineService.RestartGatewayAsync()` and `InstallUpdateAsync(version)`: operator only, and only on the service
  gateway; elsewhere `gateway.not-a-service` (the desktop's in-process engine, a container gateway).
- `UpdateStatus` gains `CanInstall` (the engine updates itself from here: the service gateway; the installed desktop
  keeps its own installer) and `Install` (where an update stands: the step, or the failure and its reason).
- Configuration: `Engine:Updates:Kind` takes `Service`, set by the unit.
- Files: `update-request.json` and `update-status.json` in the data folder; `aprsmap-gateway-update.path`,
  `aprsmap-gateway-update.service` and the updater script in the tarball's `deploy/linux`.

## APRS.NET dependencies

None.

## Desktop vs web differences

The service gateway's admin web app only, and the desktop app as its client with the key (F1.39), which has the same
notice and About. The installed desktop app keeps its own Update and restart (F4.15 behavior 11).

## Acceptance tests

1. A gateway with `Engine:Updates:Kind=Service` offers Restart and Update and restart to the operator; a container
   gateway and a viewer are offered neither, and the calls are refused with `gateway.not-a-service` or
   `gateway.operator-only`.
2. Restart stops the gateway cleanly with the exit that systemd restarts.
3. A service release is ready only with its architecture's tarball and checksum attached.
4. Update and restart writes a request with the version only; a request with anything else, an older version or a
   malformed version is refused by the updater.
5. The updater, run in a container against a fake release server: a good tarball is installed and the service
   restarted; a bad checksum, or a new version that doesn't answer, leaves the previous one running, and the status
   says why.
6. The unit files pass `systemd-analyze verify`.

## Decisions for review

1. **Update and Restart only for the Linux service** (maintainer, 2026-10-26); never for the container.
2. **Restart only through systemd** (maintainer, 2026-10-26: the Docker engine restarts a container).
3. **An unprivileged gateway and a root updater** started by systemd from a request file (proposed), rather than
   letting the service write its own program folder, so a compromised gateway can't replace its program or run
   anything as root: the request carries a version and nothing else.
4. **Checked by a SHA-256 published with the release, over HTTPS** (proposed), as the desktop's updates are; releases
   aren't signed yet (code signing is undecided). Signing the checksums can follow.
5. **Roll back when the new version doesn't answer** (proposed), keeping one previous version.
6. **Restart in About** (proposed), not in a menu, as it's rare.
7. **Restart and update need a signed-in operator or the API key** (as built), even on a gateway that lets every browser
   change settings (`AllowSettingsChanges` with no operator), since an update runs as root.
