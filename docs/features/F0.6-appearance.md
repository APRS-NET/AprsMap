# F0.6 Settings screen and appearance

Status: built (palettes and preferences in #39, the Settings screen in #41, then the accessibility checks)

## User story

As a user, I open Settings and change how the app looks (light or dark, a high-contrast or colour-vision-safe
palette, bigger text, sharper corners, a denser list, less motion, another language) and see each change at once,
without restarting. The choice is mine alone: on a gateway, other people's browsers keep their own.

As a contributor, I add a settings page or option in one place, and it is laid out, saved and found like the others.

## Behavior

### The Settings screen

1. A **Settings** button in the status bar (a gear icon with a tooltip and an accessible name) opens Settings. Until the
   app shell's rail exists (Phase 1), this button is the way in. Afterwards the rail's Settings item opens the same
   screen. Ctrl+, (Cmd+, on macOS) opens it too, bound on the window so it works wherever focus is. In the browser,
   the page has to have keyboard focus first (a click into it), as with any web app's shortcuts. Settings doesn't open
   while the setup wizard is open.
2. Settings is a page, not a dialog (UX principle 7). It replaces the main view, with a **Back** button and Esc to
   return. The live packet stream keeps running behind it, and nothing the user was doing is lost.
3. The page lists its sections down the side on a wide window (≥ 720 px) and as tabs across the top on a narrow one
   (a phone browser). F0.6 has two sections: **Appearance** and **About**. Later features add theirs
   (Profiles in F0.8, Station, Connections… in Phases 1–3) without changing this layout.
4. Every setting is declared once in a **settings registry**: its section, label key, help key, kind (choice, slider,
   toggle) and where its value lives. The page is built from the registry, so a new option needs no new view code, and
   the later command palette and settings search (UX principle 2) use the same list.
5. Changes apply **live**, as they are made. There is no Apply or OK. A **Reset appearance** button restores the
   defaults at once and offers **Undo** for 10 s, which makes a confirmation step unnecessary.

### Appearance options

Each applies to the whole app at once through theme tokens (`DynamicResource`); no view changes.

6. **Theme**: Light · Dark · Auto (default). Auto follows the OS on desktop and `prefers-color-scheme` in the browser,
   and switches live when they change.
7. **Colours**: Standard · High contrast · Colour-vision-safe. Each palette has a light and a dark variant (Theme ×
   Colours = 6 combinations), and each is a token dictionary in `AprsMap.UI/Themes/`:
   1. **Standard**: today's quiet palette ([visual style](../ux/README.md#visual-style)). Body text at least 4.5:1 and
      UI component boundaries and large text at least 3:1 against what they sit on (WCAG 2.2 AA).
   2. **High contrast**: body and muted text at least 7:1 (WCAG AAA), borders 2 px instead of 1, focus outlines 3 px.
   3. **Colour-vision-safe**: never red against green. Ok is blue, Warn orange and Transmit reddish purple, from a
      palette designed for colour-vision deficiency (Okabe and Ito), darkened or lightened to meet AA as text. Colour is
      never the only signal in any palette (UX principle 9), so every state also has an icon or text.

   Fluent's own controls (buttons, inputs, selection) follow the palette too: its accent, text, ground and error
   colours are set from the palette (`FluentTheme.Palettes`).

   When the user hasn't chosen, the default follows the OS contrast preference: High contrast when the platform
   reports `ColorContrastPreference.High` (Avalonia), Standard otherwise.
8. **Text size**: 85 %, 100 % (default), 115 %, 130 %, 150 %, 175 %, 200 %. It scales every text token. Layouts
   reflow rather than clip (behavior 21). In the browser, the browser's own zoom also still works.
9. **Icon size**: Small (16 px) · Medium (20 px, default) · Large (24 px), plus **Follow text size** (on by default),
   which scales the icon size with the text size.
10. **Corners**: Rounded (default: 8 px controls, 12 px panels) · Sharp (2 px and 0 px).
11. **Density**: Comfortable (default) · Compact, which tightens list rows and paddings (our `Space.ListItem` and
    `Size.ListItemMinHeight` tokens, and Fluent's own `DensityStyle`). On a touch screen (the primary pointer is
    coarse) touch targets stay at least 44 × 44 px in either density.
12. **Motion**: Follow system (default) · Reduced. In the browser, Follow system reads `prefers-reduced-motion`. On
    desktop the OS setting isn't available to the app yet (Avalonia doesn't report it), so Follow system means normal
    motion and the user picks Reduced themselves. Reduced turns transitions off (a `Motion.Duration` token of 0).
13. **Language** (from F0.9): System default · each translated language, in its own name, plus the pseudo-language
    when shown (F0.9 behavior 6). It switches live.
14. **Map symbol size** (75 %–200 %) is stored now but shown only once the map exists (F1.4). An option that does
    nothing is not shown.

### About

15. **About** shows the product name and version (`Brand.DisplayName`, `Brand.Version`), the licence (AGPL-3.0 for the
    app, MIT for the engine), a **Source code** link (`Brand.SourceUrl`; the AGPL network-use offer), the APRS.NET
    version, and credits: OpenStreetMap and Nominatim (when address lookup is on), and the app icon. On the web it also
    shows the gateway's version from `EngineStatus.EngineVersion`.

### Saving

16. Appearance is **per viewer**, never part of the station's `AppSettings`, and never sent to the engine (UX doc,
    "Appearance is per viewer"). A platform service, `IPreferenceStore`, which each app supplies like
    `IDeviceLocation`, loads and saves it:
    - **Desktop**: `appearance.json` in the user's settings folder, next to the engine's `settings.json`
      (`SettingsLocation`, F0.4).
    - **Browser**: the browser's `localStorage`, under a key that starts with `Brand.Slug`.

    A gateway never sees one viewer's appearance, and two browsers on one gateway keep their own.
17. Saving happens a moment after the last change (debounced, about 0.5 s), so dragging a slider doesn't write on
    every step. Writes are atomic on desktop, as for `settings.json`.
18. An unreadable or missing store means defaults, never an error dialog. Examples: a private browsing window that
    refuses `localStorage`, or a file that fails to parse (moved to `.invalid`, as F0.4 does). Unknown values (from a
    newer version) are ignored one by one; the rest still load.
19. Appearance loads **before the first window is shown**, so the app doesn't flash in the wrong theme or language.
    On the web, the loading page (`index.html`) follows `prefers-color-scheme` already.

### Accessibility and appearance of the screen itself

20. Settings works with the keyboard alone: Tab order follows the visual order, arrow keys move within a choice, and
    focus starts on the first section's first option. Every control has an accessible name from its label. Focus is
    always visible.
21. Every screen of the app (today: the main view, the wizard with its calculator, and Settings) renders without
    clipping in all six Theme × Colours combinations at 100 % and 200 % text (headless tests).
22. The settings page itself uses only theme tokens and translated strings, like every view (F0.9 guards).

## Service surface

- **No `IEngineService` change.** Appearance is per viewer and lives in the UI layer.
- **New platform service** `AprsMap.UI.Platform.IPreferenceStore`: `LoadAsync(key)`, `SaveAsync(key, value)` and
  `SetAsideAsync(key)` (behavior 18), never throwing for an unavailable store. Desktop: `FilePreferenceStore`, a JSON
  file per key in the settings folder (`SettingsLocation.Folder`). Browser: `BrowserPreferenceStore`, `localStorage`
  through `main.js`. Tests: in memory. `AppearancePreferences` reads each value on its own (`JsonDocument`), so it is
  trim-safe and skips what it doesn't know.
- **`PlatformServices`** carries what each app supplies to the shared UI: the device location (F0.5), the preference
  store, the appearance loaded before startup, and the browser's reduced-motion preference.
- **Palettes** are compiled `ResourceDictionary` classes (`Themes/Palettes/*.axaml` with `x:Class`), swapped in by
  `AppearanceService`. Loading XAML at runtime (`ResourceInclude` in code) isn't trim-safe in the browser build.
- `AppearanceSettings` gains `Motion`, `Density`, `IconsFollowText`, `MapSymbolScale` and the `Language` from F0.9, and
  is versioned for behavior 18.
- `AppearanceService` gains the palette dictionaries (behavior 7) and the density and motion tokens.

## Acceptance tests

1. Opening Settings (button, and Ctrl+,) shows the Appearance section; Back and Esc return to the main view with the
   packet list still updating.
2. Each option changes its tokens at once: theme variant, the palette's colours, text sizes, icon size (and with
   Follow text size), corner radii, density paddings, motion duration (unit tests on `AppearanceService.Tokens`, plus a
   headless render).
3. Contrast: for each of the 6 combinations, every text colour (Text, TextMuted, Accent, Ok, Warn, Transmit) on
   Ground and Surface, and Text on AccentSoft, meets 4.5:1 (Standard, Colour-vision-safe) or 7:1 (High contrast).
   High-contrast borders meet 3:1. A unit test computes the WCAG ratios from the palette files. (Standard's thin
   separators are decorative, so 1.4.11 doesn't apply to them.)
4. Colour-vision-safe: under simulated protan, deutan and tritan vision (Machado et al. 2009, full severity), Ok, Warn
   and Transmit stay at least ΔE 15 apart (CIE 1976) in both modes, and Ok is on the blue side.
5. With no stored choice and the platform reporting high contrast, the default palette is High contrast.
6. Saving: changes are written once after a burst of changes; a fresh start loads them before the first window; a
   corrupt or unavailable store gives defaults without an error; an unknown value is ignored and the rest load.
7. Two browsers on one gateway keep different themes (gateway test with two `IPreferenceStore`s).
8. Keyboard-only: open Settings, change every option, reset with Undo, and go back (headless).
9. Every screen renders without clipping in all six combinations at 200 % text (headless).
10. About shows the version and a working Source code link; the guards find no literal text in the new views.

## Decisions for review

1. **Settings search**: build the search box now, or when the second section with options arrives (Profiles, F0.8)?
   The registry (behavior 4) makes it cheap either way. Proposed: with F0.8.
2. **About** in F0.6 (behavior 15): it is small and gives the AGPL source link a permanent home in the UI. Proposed:
   yes.
3. **Default palette from the OS contrast preference** (behavior 7). Proposed: yes; the user's own choice always wins.
4. **Text size steps** (behavior 8): fixed steps, or a continuous slider? Proposed: steps, which test and reflow
   predictably.
