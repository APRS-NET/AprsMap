# F1.37 The gateway as a Linux service, configured in TOML

Status: scoped for 0.8.0 ([#398](https://github.com/APRS-NET/AprsMap/issues/398), maintainer request, 2026-10-26); decisions proposed.

## User story

As an operator with an always-on Ubuntu PC that has the TNC on USB and gpsd running, I install the gateway as a system
service, describe it in one TOML file (where it listens, where it keeps its data, the station's first-run callsign, the
USB TNC and gpsd), and it starts with the computer. Anyone on the network can watch the published, read-only web app;
the admin web app, where the station is changed and where apps with the API key connect, listens only on the PC
itself unless I say otherwise.

## Background: what already exists

- The gateway (F1.14) runs from the container image only. It reads `appsettings.json`, environment variables and the
  command line; first-run defaults for the callsign, passcode, server, filter and a KISS over TCP source come from
  `Engine:*` (docs/deployment.md).
- Two ports (F1.26): the **viewer port** (`8080`), always read-only and never offering sign-in, and the optional
  **operator port** (`Gateway:OperatorPort`, for example `8081`), where operators sign in (F2.9). Both listen on every
  address; keeping the operator port private is left to the deployment (Compose binding it to loopback).
- Operators are set up with `aprsmap-gateway operator add NAME`.

## Behavior

1. **A TOML configuration file**, `/etc/aprsmap/gateway.toml` for the service, or any path with `--config PATH` (or
   `APRSMAP_CONFIG`). Tables and keys map onto the gateway's configuration: `[gateway]` is `Gateway:*`, `[engine]` is
   `Engine:*`, and so on, with `snake_case` keys read as the settings' names (`operator_listen` is `OperatorListen`).
   It sits between `appsettings.json` and environment variables, so an environment variable still wins. A file that
   can't be read stops the gateway at start with the line and the reason, rather than starting with defaults.
2. **Where it listens**, as `address:port`:
   1. `[gateway] listen`, the published read-only web app: `0.0.0.0:8080` by default (every address);
   2. `[gateway] operator_listen`, the admin web app (the operator port): **`127.0.0.1:8081` by default in the
      service's file**, so it's reachable only on the PC itself; set `0.0.0.0:8081` (or a LAN address) to reach it from
      the network, where signing in or the API key (F1.38) is still needed. Left out, there's no admin port, as now.
   `Gateway:OperatorPort` and `ASPNETCORE_HTTP_PORTS` keep working; `operator_listen` wins over `OperatorPort`.
3. **Where it keeps its data**: `[engine] settings_folder` (settings, operators, the API key, message history, the
   dashboard's history, tiles), `/var/lib/aprsmap` for the service.
4. **First-run station**, as now from `[engine]`: `callsign`, `passcode`, `server`, `filter`, `receive_only`; and two new
   first-run sources, added to the first profile when there are no settings yet:
   1. `[engine.kiss_serial]`: a USB TNC, `port` (such as `/dev/serial/by-id/usb-…`), `baud` (9600), `tnc_port`,
      `name`;
   2. `[engine.gpsd]`: gpsd, `host` (`localhost`), `port` (2947), `name`.
   After the first run the stored settings win, as for the other first-run values, and the admin web app changes them.
5. **The service**: a systemd unit, `aprsmap-gateway.service`, that runs the gateway as its own user (`aprsmap`, in the
   `dialout` group for the TNC), with the state directory `/var/lib/aprsmap` and the configuration directory
   `/etc/aprsmap`, restarts it if it stops, and logs to the journal. A sample `gateway.toml`, commented, and an install
   script that puts a release's gateway in `/opt/aprsmap-gateway`, creates the user and folders, installs the unit
   and the sample (never over an existing file), and enables the service.
6. **A gateway release for Linux**: each release adds `aprsmap-gateway-vX-linux-x64.tar.gz` and `…-linux-arm64.tar.gz`,
   self-contained, with the browser app in `wwwroot`, and in the SBOM (F4.17).
7. **Ports differ from the desktop app's**: the gateway's 8080 and 8081, the desktop web viewer's 8090 (F1.35), so the
   gateway and a desktop app (F1.39) run side by side on one PC.

## Service surface

None on `IEngineService`. Configuration: `Gateway:Listen`, `Gateway:OperatorListen`, `Engine:KissSerial:*`,
`Engine:Gpsd:*`; `--config` and `APRSMAP_CONFIG`.

## APRS.NET dependencies

None.

## Desktop vs web differences

Gateway only.

## Acceptance tests

1. A TOML file with tables and `snake_case` keys sets the matching settings; an environment variable wins over it; a
   malformed file stops the gateway with its line.
2. `listen` and `operator_listen` bind those addresses: the viewer port answers on every address, the operator port
   only on loopback by default.
3. A first run with `[engine.kiss_serial]` and `[engine.gpsd]` gives a profile with both sources; a later run keeps the
   stored ones.
4. The unit file and sample pass `systemd-analyze verify`; the install script, run in a container, installs and starts
   the service against a fake serial port.
5. A release has the two gateway tarballs.

## Decisions for review

1. **TOML as a configuration source** (maintainer request) beside the others, not instead of them, with `snake_case`
   keys mapped to the settings' names (proposed).
2. **The admin port on loopback by default in the service's file** (maintainer request); the code's default stays "no
   admin port" so existing containers don't change.
3. **First-run sources only**: after the first run, the admin web app owns the sources (proposed), as for the
   other first-run values.
4. **Self-contained tarballs** (proposed): nothing to install but the gateway; the user's .NET isn't needed.
