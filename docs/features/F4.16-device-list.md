# F4.16 Device list updates

Status: spec'd for 0.6.0, decisions agreed 2026-10-19. A maintainer request (2026-10-19): the list that names a station's equipment
(the APRS Foundation's aprs-deviceid list) reaches APRS.NET within a day, but AprsMap only gets it with its next
release, so an install that isn't updated never learns new devices. With internet access, the app should fetch the
list itself and use whichever is newer: the one it downloaded, or the one built into APRS.NET.

## User story

As a user, a station running a radio or app released after my copy of AprsMap still shows what it is, because the app
keeps its device list up to date by itself, about once a week, and I can update it now when I want. Offline, it uses
the list it came with. As a gateway operator, I can point it at a mirror, or turn downloading off.

## Background: what already exists

- APRS.NET's `AprsNet.DeviceId` builds the list into the package (`AprsDevices`, with the list's `ListCommit` and
  `ListDate`). Its nightly workflow fetches the published list and opens a pull request when it changes, so each
  APRS.NET release carries the list as it was then.
- AprsMap names a station's device from its last packet (`StationFacts.Device`, F1.6): its destination (TOCALL), or
  for Mic-E the codes around its comment.
- The APRS Foundation publishes the list at `https://aprs-deviceid.aprsfoundation.org/tocalls.pretty.json` (and a dense
  form). The file carries `meta.generation_time`, and the server answers with an `ETag` and `Last-Modified`, so a check
  that finds nothing new costs one `304 Not Modified`.
- The list is CC BY-SA 2.0, by Heikki Hannikainen, OH7LZB, and its contributors.

## Behavior

### Which list is used

1. **Two lists**: the one built into APRS.NET (the **built-in list**), and the last one downloaded and checked (the
   **downloaded list**), kept unchanged in the cache folder (`deviceid/tocalls.json`, F4.15 behavior 13).
2. **The newer one is used**: the one whose `generation_time` is later. A downloaded list older than the built-in one
   (after the app is updated) is ignored and deleted. A downloaded list that can't be read is ignored and deleted, and
   the built-in list is used; the problem shows in Settings › Data (behavior 9).
3. **Switching lists takes effect at once** for new packets, and **stations already heard are identified again** from
   their last packet (maintainer, 2026-10-19), so a device the old list didn't know fills in without waiting for the
   station's next beacon.

### Checking for a newer list

4. **Check automatically** is **on**, **weekly** by default (maintainer, 2026-10-19): Off, Daily or Weekly, in
   Settings › Data. The first check is a few minutes after start when the last one was longer ago than the interval;
   the time of the last check and its result are kept with the settings, so restarting doesn't check again.
5. **Update now** in Settings › Data checks at once, whatever the schedule.
6. **One anonymous request**: a `GET` of the list, with the app's User-Agent (`Brand.Slug`/`Brand.Version` and
   `Brand.SourceUrl`, as F0.5 behavior 17) and `If-None-Match` with the downloaded list's `ETag`. Nothing about the
   station is sent. `304` means unchanged. A new list is checked before it's kept (behavior 8).
7. **Nothing is fetched while the Internet switch is off** (F1.15), and a scheduled check waits for it to be on again.
8. **A downloaded list is kept only when** APRS.NET reads it without error (the same rules its generator applies), it
   has TOCALL entries, and its `generation_time` is later than the list in use. Otherwise it's thrown away and the
   result says why (`devicelist.unreadable`, `devicelist.not-newer`).

### Where it's set and shown

9. **Settings › Data › Device list**: the list in use ("Built in, from 18 October 2026" or "Downloaded, from 25 October
   2026"), the last check and its result ("Checked today: up to date", "Couldn't reach the server"), **Update now**,
   and **Check automatically** (Off, Daily, Weekly).
10. **The address** is `DeviceList:Url` in `appsettings.json` or the environment (`Engine__DeviceList__Url`), the APRS
    Foundation's by default, for a mirror or a gateway on a closed network; an empty address turns downloading off and
    hides Update now and the schedule. On the desktop, Settings › Data has the same address under **Advanced**, with
    Reset to the default (maintainer, 2026-10-19).
11. **Help › About** says which list is in use and its date, and credits it: "Device names: the aprs-deviceid list by
    OH7LZB and contributors, CC BY-SA 2.0", with a link to the list.

### On a gateway

12. The gateway's engine keeps the list and checks for it, as on the desktop. **Update now**, the schedule and the
    address are the operator's (F2.9); viewers see which list is in use and its date. The address set by the
    environment can't be changed from a browser.

## Service surface

- `DeviceListSettings(DeviceListSchedule Schedule = Weekly, string? Url = null)` in `AppSettings` (`DeviceList`);
  `DeviceListSchedule`: `Off`, `Daily`, `Weekly`. A null `Url` means the configured one (behavior 10).
- `DeviceListStatus(DeviceListSource Source, DateTimeOffset GeneratedAt, string? Commit, DateTimeOffset? LastChecked,
  EngineError? LastError, bool CanDownload)`; `DeviceListSource`: `BuiltIn`, `Downloaded`.
- `Task<DeviceListStatus> GetDeviceListAsync()` for everyone; `Task<DeviceListStatus> UpdateDeviceListAsync()`
  operator-only on a gateway (`gateway.operator-only`); `EngineStatus` gains `DeviceList` so a change shows without
  asking.
- Error codes: `devicelist.unreachable`, `devicelist.unexpected-answer`, `devicelist.unreadable`,
  `devicelist.not-newer`.
- Configuration: `Engine:DeviceList:Url` (default the APRS Foundation's address; empty turns downloading off),
  `Engine:DeviceList:Timeout` (30 s).
- The engine (MIT `AprsMap.Core`) owns the schedule, the cache file and the choice of list; it asks APRS.NET to read and
  fetch the list (G35). `StationFacts.Device` takes the list in use instead of the static `AprsDevices`; the station
  store re-identifies its stations when the list changes (behavior 3).

## APRS.NET dependencies

**G35, the device list as a loadable object, and a fetcher for it** (proposed, APRS.NET 0.6.0):

1. `AprsDeviceList`: the built-in list (`AprsDeviceList.BuiltIn`), or one read from the published JSON
   (`AprsDeviceList.Parse(Stream)` / `TryParse`, with the reasons it can't, under the generator's rules), with
   `GeneratedAt`, `Commit` (when known) and the lookups `Identify(AprsPacket)` and `FromTocall(string)`. The static
   `AprsDevices` keeps working, on `BuiltIn`.
2. `AprsDeviceListSource`: fetches the list from an address (default `AprsDeviceListSource.DefaultUrl`, the APRS
   Foundation's), with an injected `HttpClient`, sending `If-None-Match`, and answers *unchanged*, a new
   `AprsDeviceList` with its `ETag`, or why it failed. Mirrors pass their own address.
3. `AprsDeviceList.IsNewerThan(other)` by `GeneratedAt`, so every app decides "newer" the same way.

Until G35 ships, nothing here is built: reading the list's format is APRS.NET's (CLAUDE.md, ownership), and a shim would
copy its generator.

## Desktop vs web differences

| | Desktop | Web (gateway) |
| --- | --- | --- |
| Who updates | The user | The operator; viewers see which list |
| Address | Settings › Data › Advanced, or `appsettings.json` | `Engine__DeviceList__Url` |
| Where the list is kept | The cache folder (F4.15 behavior 13) | The gateway's cache volume |

## Acceptance tests

1. With no downloaded list, the built-in one is used and Settings › Data says "Built in" with its date.
2. Against a fake server: a list with a later `generation_time` is downloaded, kept, used, and a station heard with a
   TOCALL only it knows gets its device named at once (behavior 3); the next check sends `If-None-Match` and a `304`
   changes nothing.
3. A list that isn't newer, one that can't be read and one with no TOCALLs are thrown away with
   `devicelist.not-newer` and `devicelist.unreadable`; the list in use doesn't change.
4. A downloaded list older than the built-in one (after an app update) is deleted on start, and the built-in one is
   used.
5. The schedule: Weekly checks once in seven days across restarts; Off never checks by itself; Update now always does;
   nothing is fetched with the Internet switch off.
6. An empty `DeviceList:Url` hides Update now and the schedule and never fetches.
7. On a gateway, a viewer's Update now is refused with `gateway.operator-only`, and the viewer sees the list in use.
8. About credits the list (CC BY-SA 2.0, OH7LZB and contributors) and names the one in use.

## Decisions

Agreed with the maintainer (2026-10-19):

1. **Split between APRS.NET and the app.** Reading, checking and fetching the list (with a default address that can be
   overridden for mirrors) are APRS.NET's (G35), so every APRS.NET user gets them; when to check, where the copy is
   kept, which list is used, and the settings are the app's.
2. **Weekly, on by default**: the list changes a few times a month, and an unchanged check is one `304`.
3. **Stations already heard are identified again** when the list changes.
4. **The address is configurable** in `appsettings.json` or the environment, and on the desktop in Settings › Data ›
   Advanced; empty turns downloading off.
5. **Settings › Data** shows the list and Update now; **About** names it and credits it.

6. **Newer by `generation_time`**: the list's own timestamp, which the built-in list carries too, rather than the
   commit date (a download doesn't carry it) or the HTTP `Last-Modified` (a mirror's own copy time).
7. **The downloaded file is kept as published**, not converted, so it's the list exactly as its licence gives it, and
   APRS.NET reads it again on each start (about 70 KB).
8. **G35 is a list object**: apps pass the `AprsDeviceList` they use, and the static `AprsDevices` stays on the
   built-in list, rather than a static that could be switched for the whole process.
