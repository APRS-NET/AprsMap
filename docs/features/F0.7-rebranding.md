# F0.7 Rebrandable product

Status: built

## User story

As the maintainer, I can rename the product ("AprsMap" is a working name) with one script run and a review, and users
keep their settings across the rename. As a contributor, I can't accidentally hard-code the name where a rename would
miss it.

## Behavior

1. **One source.** The product's identity lives in `build/Branding.props`: `ProductName` (code and prose),
   `ProductDisplayName` (what users see), `ProductSlug` (folders, the container image, URLs, storage keys),
   `PreviousSlugs`, `ProductTocall` and the URLs. Every project gets them as assembly metadata, read by `Brand` in
   Contracts (`Brand.DisplayName`, `Brand.Slug`, `Brand.Version`, `Brand.SourceUrl`, `Brand.Tocall`).
2. **User-visible text never names the product literally.** Views bind to `Brand.DisplayName`; translated strings take
   it as a `{product}` placeholder (F0.9). A CI guard fails on a UI string that contains the product name.
3. **The name is only a namespace or project prefix** (`AprsMap.Core`), never part of a type name, so a rename is a
   prefix swap ([branding.md](../branding.md), rule 2).
4. **`tools/rename-product.py OLD NEW [--apply]`** replaces the three spellings (`AprsMap`, `aprsmap`, `APRSMAP`) in
   file contents and paths, skipping `.git/`, licences, binaries and the clean-room exposure log, and appends the old
   slug to `PreviousSlugs`. The dry run lists what would change.
5. **User data survives.** Settings (`settings.json`, `appearance.json`) are found through `Brand.Slug`; on first start
   after a rename the app copies the previous slug's folder (F0.4, `SettingsLocation.MigrateIfMissing`). The browser's
   `localStorage` keys start with the slug, so a renamed web app starts with default appearance.
6. **Not renamed:** the transmitted TOCALL (a registered device ID; a new one is a separate decision) and the app icon
   (the APRS.NET icon).
7. **The rename keeps working:** the `rename-check` workflow renames a copy of the repository to a test name, then
   builds and tests it. It runs weekly, and on pull requests that change the rename script, `Branding.props` or the
   workflow itself.

## Acceptance tests

1. The guard test fails when a string in `Strings.resx` contains the product name.
2. `rename-check` passes: after renaming to `SkyTrack`, the solution builds in Release with warnings as errors, every
   test passes, and only `PreviousSlugs` still mentions the old slug.
3. Settings migration from a previous slug's folder (F0.4 test `SettingsFromAPreviousNameAreCopiedOnce`).
