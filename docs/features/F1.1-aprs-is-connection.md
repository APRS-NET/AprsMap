# F1.1 APRS-IS connection

Status: done ([#65](https://github.com/APRS-NET/AprsMap/issues/65))

## User story

As an operator, I connect to APRS-IS as the active profile and stay connected through server restarts, network
drops and laptop sleep, without doing anything. When the connection is down, I see why and when it will try again;
when my login is refused, I'm told so rather than having the app hammer the server. Changing the filter doesn't drop
the connection.

Built (F0.2, F0.4, then this feature): connecting with the active profile, reconnecting on a profile change, and the
connection state in the status bar; with APRS.NET `0.2.0-alpha.1`, the engine runs on `AprsIsConnection` and the
`// SHIM: G03` loop is gone (#61); then behaviors 3–9 (#65). Not built: the `aprs-is.no-packets` reason, because the
engine doesn't set `MaxPacketSilence` (a quiet filter area can legitimately go minutes without a packet; the server's
keepalives and `IdleTimeout` catch a dead link).

## Behavior

### Staying connected

1. The engine keeps one APRS.NET `AprsIsConnection` (G03, `0.1.0-alpha.17`) for the active profile. It reconnects by
   itself when the server closes, the link fails, the server goes silent (`IdleTimeout`) or no packet arrives for
   `MaxPacketSilence`: it waits `ReconnectDelay` (5 s), doubling up to `MaxReconnectDelay` (60 s) with ±20 % jitter, and
   resends the login and filter. AprsMap's own loop (`Engine.RunAsync`, `// SHIM: G03`) is removed.
2. The packet stream is continuous across reconnects (`ReadLinesAsync`), so the map, the packet list and the counts
   carry on without resetting.
3. **The first connection** is different: APRS.NET reports a failure at once (`StartAsync` throws).
   - **Unreachable** (DNS, refused, timeout): the engine retries with the same backoff, showing each wait.
   - **Login refused** (`LoginRejectedException`, for example `N0CALL` or a banned login): the engine does **not**
     retry by itself. It shows the refusal with the server's reason, and waits for a profile change or **Reconnect
     now** (behavior 7). Retrying a refused login on a timer only adds load to the servers.

### Status

4. `EngineStatus` carries the state from `AprsIsConnection.StateChanged`:

   | State | Status bar text (en) |
   | --- | --- |
   | Not set up | APRS-IS not set up · add a callsign (as now) |
   | Connecting | APRS-IS connecting to *server*… |
   | Connected | APRS-IS connected · *server* (verified when the login is) |
   | Reconnecting | APRS-IS reconnecting in *n* s · *why* |
   | Refused | APRS-IS login refused · *reason* |
   | Disconnected | APRS-IS disconnected (engine stopped, or APRS-IS turned off) |

   "Why" is what ended the last connection: server closed, link failed, server silent, no packets. The countdown counts
   down in the UI from `RetryAt` (a time, so every viewer sees the same moment).
5. The reasons travel as `EngineError` codes (F0.9), translated in the UI: `aprs-is.unreachable`,
   `aprs-is.login-refused` (with the server's text as an argument), `aprs-is.server-closed`, `aprs-is.link-failed`,
   `aprs-is.idle` (and `aprs-is.no-packets` if `MaxPacketSilence` is ever set).
6. The status also shows whether the login is verified (a passcode accepted) and how many times the connection has
   been re-established since it started (`Reconnects`), in the connection's tooltip and in About.

### Acting on it

7. **Reconnect now**: clicking the connection text in the status bar offers Reconnect now, which closes the current
   connection and starts a new one at once, resetting the backoff. On a gateway it is operator-only, like settings
   changes, because it affects every viewer.
8. **Filter changes don't reconnect**: when only the active profile's filter changes, or its location changes while
   it has no filter of its own (the 150 km stand-in moves), the engine calls `SetFilterAsync` on the live connection.
   A login, passcode or server change still reconnects (F0.4). `StationProfile.ConnectsDifferentlyFrom` is split into
   "needs a new login" and "needs a new filter".
9. **Turning APRS-IS off** (the quick toggle is F1.15; until then `Engine:Enabled`) disposes the connection; the state
   becomes Disconnected.

### Server choice

10. The server comes from the profile (F0.5, F0.8): an aprs2.net rotate by default, whose DNS spreads clients across
    the Tier 2 servers. A list of servers to rotate through (G03's "endpoint list") isn't needed for this: a rotate
    hostname already does it, and a single named server is the user's explicit choice.

## Service surface

- `ConnectionState` gains `Reconnecting` and `Refused`.
- `EngineStatus` gains `Verified` (bool), `RetryAt` (`DateTimeOffset?`), `Reconnects` (int) and `ConnectionError`
  (`EngineError?`).
- New `IEngineService.ReconnectAsync()`; on the gateway it has the same gate as `SaveSettings`.
- Engine: `IPacketSource` is a long-lived connection over `AprsIsConnection`: start (returning the server and whether
  the login is verified, with a callback for later state changes), a packet stream across reconnects, and set filter.
  Tests keep a fake.

## APRS.NET dependencies

- **G03**, delivered in `0.1.0-alpha.17` as `AprsIsConnection` (reconnect with backoff and jitter, one line stream,
  filter kept across reconnects, state events). Endpoint-list rotation from G03's original scope isn't needed
  (behavior 10).

## Acceptance tests

1. With a fake transport and clock: a dropped connection reconnects after the backoff, the line stream continues, and
   the counts don't reset.
2. The status walks Connecting → Connected → Reconnecting (with `RetryAt` and the reason) → Connected, and the UI
   shows the countdown and reason in every language (pseudo-language check).
3. An unreachable first connection retries with backoff; a refused login doesn't retry until the profile changes or
   Reconnect now.
4. A filter-only change sends the new filter without a new login; a callsign change logs in again.
5. Reconnect now resets the backoff; on a read-only gateway it is refused with `gateway.operator-only`.
6. Live: against the fake APRS-IS server, stopping and restarting it shows Reconnecting with a countdown, then
   Connected again with the packet list continuing.

## Decisions for review

1. **Refused logins don't retry by themselves** (behavior 3). Proposed: yes. The alternative is a slow retry (say every
   10 minutes).
2. **Reconnect now on a gateway is operator-only** (behavior 7). Proposed: yes, as for every action that changes the
   station for all viewers.
