# F2.9 Gateway operator sign-in

Status: built for 0.5.0 ([#191](https://github.com/APRS-NET/AprsMap/issues/191)), with behavior 8.2 (sign-in only on F1.26's
operator port). Signing in or out starts the web app again, so the hub connects with the new role and the
settings open up. Sessions are kept in memory, so restarting the gateway signs everyone out.

## User story

As the operator of a gateway, I sign in from my browser with a password only I know, and only then can I transmit,
change the station or type to its TNC. Everyone else who opens the page can watch but never act for the station, and if
someone guesses at my password the gateway slows them down and tells me.

## Background: what already exists

- **Desktop** has no viewers: whoever runs the app is the operator. Nothing here changes it.
- **Gateway, today** (F1.14, F1.26): `Gateway__AllowSettingsChanges` (off by default) lets every browser change
  settings; F1.26's operator port gives the operator role to whoever reaches that port. Neither is a sign-in: both trust
  the network. Every transmit call is refused from a browser outright (F2.1 behavior 9, F2.4 behavior 16, F3.2 behavior
  12) whatever those say.
- The hub already checks a role on every call that changes the station (`gateway.settings-read-only`,
  `gateway.operator-only`); this feature decides that role by sign-in.

## Behavior

### Operators

1. **Operators are set up on the gateway's host**, never from a browser: one or more, each a name and a password hash,
   in `/data/operators.json`. The gateway image has a command to add one, change a password or remove one:
   `docker exec -it aprsmap aprsmap-gateway operator add NAME`, which asks for the password twice and stores its hash.
   A hash can also come from the environment (`Gateway__Operators__0__Name`, `Gateway__Operators__0__PasswordHash`) or
   a secrets file; a plain password is never read from configuration.
2. **Passwords** are at least 12 characters; they're stored as salted PBKDF2-SHA256 hashes with a high iteration count
   (decision 2), compared in constant time, and never logged.
3. **Changing or removing an operator's password ends their sessions** at once.

### Signing in

4. With at least one operator set up, the web app shows **Sign in** in the app menu. It asks for the name and password
   in a dialog and posts them to the gateway's `/auth/sign-in`, not over the hub.
5. A good sign-in gives the browser a **session cookie**: `__Host-` prefixed, HttpOnly, Secure, SameSite=Strict,
   signed and encrypted with keys kept in `/data/keys`. It lasts **12 hours from the last use, and 7 days at most**
   (decision 3). The hub connection reconnects, and the new role applies to it.
6. **Sign out** (app menu, beside "Signed in as NAME") ends the session on the gateway, not just in the browser.
7. A wrong name or password gets the same answer, "That name and password don't match", after the same delay, so the
   answer doesn't say which was wrong.
8. **Where sign-in is offered**:
   1. Over **HTTPS** only: the gateway refuses `/auth/sign-in` over plain HTTP unless the request came from the host
      itself (loopback) or from a trusted proxy (F1.14's `KnownProxies`) that says it was HTTPS. The dialog says why.
   2. With F1.26's **operator port** configured, sign-in is offered **only there**; the viewer port never offers it
      (decision 4). The operator port then needs a sign-in too, instead of trusting whoever reaches it.

### Guessing

9. **Failed sign-ins are limited**: 5 from one address in 15 minutes, then that address waits 15 minutes; 10 for one
   operator name in an hour, then that name waits an hour, from every address. Waits are answered with "Too many tries,
   wait N minutes" and nothing is checked meanwhile.
10. **Every sign-in, failed sign-in, wait and sign-out is logged** with the time, the address (after the trusted proxy)
    and the name tried, never the password, and counted in the gateway's metrics. Failed sign-ins in the last day show
    to a signed-in operator in Help › About (decision 5).

### What the role allows

11. **Viewer** (not signed in): what F1.14 and F1.26 give a viewer. Nothing that transmits or changes the station.
12. **Operator** (signed in): everything that changes the station (what `AllowSettingsChanges` allows today) and
    everything that transmits: the Transmit switch, Send position now, Test send, messages, beacon settings, the TNC
    command line and manual mode (F3.2), the Source console (F1.28) and packet capture (F1.27).
13. **The role is checked by the gateway on every hub call**, from the session the connection was opened with, and the
    hub connection ends when the session does (sign-out, expiry, a password change). Nothing the browser sends picks
    the role.
14. **The engine's own rules still apply**: a signed-in operator transmits only with a licensed profile, a source that isn't RX
    only and the Transmit switch on (F2.1), and never with `Engine__ReceiveOnly` (F1.26 behavior 7).
15. **Every transmit is logged with the operator's name** (what, on which source), on top of what the engine logs.

### Cross-site requests

16. The hub's negotiate and WebSocket requests, and `/auth/*`, are refused unless their `Origin` is the gateway's own
    (or one listed in `Gateway__AllowedOrigins`), so another site can't use a signed-in operator's browser.

### Upgrading

17. **`Gateway__AllowSettingsChanges`** keeps working for a gateway with no operators set up, as today (every browser
    may change settings; still never transmit). Once an operator exists it's ignored, with a warning at start: the
    sign-in decides. The F1.26 operator port works the same way.

## Service surface

- Gateway HTTP endpoints (not the hub): `POST /auth/sign-in` (`{ name, password }` → 204 and the cookie, 401, or 429 with
  the wait), `POST /auth/sign-out`, `GET /auth/me` (`{ role, name, expiresAt }`).
- `IEngineService` is unchanged; refusals stay `gateway.operator-only` (an `UnauthorizedAccessException`).
- `EngineStatus` gains nothing; the role is the browser's, from `/auth/me`. The UI's platform layer gets an
  `IOperatorSession` (sign in, sign out, who): the browser's implementation calls `/auth/*`; the desktop's is always the
  operator and offers no sign-in.
- New error codes for the dialog: `auth.wrong-credentials`, `auth.too-many-tries` (with the wait), `auth.needs-https`,
  `auth.not-offered-here`.
- Gateway command: `aprsmap-gateway operator add|password|remove|list NAME`.

## APRS.NET dependencies

None.

## Desktop vs web differences

| | Desktop | Web (gateway) |
| --- | --- | --- |
| Who is the operator | Whoever runs the app | Whoever signs in |
| Sign in / out | Not shown | App menu |
| Transmit, settings, TNC commands | Always (with the engine's rules) | Signed in only |

## Acceptance tests

1. With no operators, the gateway behaves as today (`AllowSettingsChanges` decides settings; transmit refused).
2. `operator add` stores a PBKDF2 hash, never the password; a password under 12 characters is refused.
3. A good sign-in over HTTPS sets a `__Host-` cookie with HttpOnly, Secure and SameSite=Strict; the hub then allows the
   Transmit switch and Send position now; a viewer's calls are still refused.
4. A wrong password and an unknown name get the same answer in the same time.
5. The sixth failure from one address in 15 minutes is answered with a wait and isn't checked; the eleventh for one name
   in an hour likewise from a second address; each is logged without the password.
6. Over plain HTTP from another machine, sign-in is refused with `auth.needs-https`; from loopback it's allowed.
7. With an operator port, sign-in on the viewer port is refused with `auth.not-offered-here`.
8. Sign-out, expiry and a password change each end the session and the hub connection.
9. A hub negotiate request with another site's `Origin` is refused.
10. Every transmit by a signed-in operator is logged with the operator's name.

## Decisions for review

1. **Passwords now, OIDC later** (proposed): a home gateway has one or two operators and no identity provider; OIDC
   (sign in with an existing account) can be added beside it without changing the roles.
2. **PBKDF2-SHA256** (proposed), as ASP.NET Core's own password hasher uses, with its current iteration count, rather
   than a new dependency for Argon2.
3. **12 hours idle, 7 days at most** (proposed) for a session.
4. **Sign-in only on the operator port when there is one** (proposed): a public viewer port never shows a password box.
5. **Failed sign-ins shown to the operator** (proposed), not only logged.
6. **No accounts from the browser** (proposed): operators are added on the host, so a web page can't create one.
