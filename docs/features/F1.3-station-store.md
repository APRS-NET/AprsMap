# F1.3 Station store

Status: built ([#66](https://github.com/APRS-NET/AprsMap/issues/66))

Built: entries for every packet type, objects and items with owners and kills, third-party packets, aging on the
engine's clock with the times in the station's settings, the entry cap, `GetStationAsync`, and duplicates not applied
again (behaviors 1–14). The two times are set in
Settings › Map (F1.4, #89).

## User story

As an operator, every station, object and item I hear has one current entry: where it is, what it is, when it was
last heard and by which path. Objects belong to whoever sent them and disappear when they're killed. Stations that
have gone quiet fade and then leave, so the map shows what is on the air now. The same packet arriving twice isn't
counted twice. This works the same on desktop and through a gateway, and stays within a bounded amount of memory.

Built already (F0.2): the engine keeps each station's latest position, keys objects and items by name, removes killed
ones, and streams changes to the map in coalesced batches. This feature completes the store.

## Behavior

### Entries

1. One entry per **station** (keyed by the packet's source callsign with SSID), per **object** and per **item** (keyed
   by name, since objects and items are global by name in APRS).
2. An entry holds: kind (station, object, item), name, latest position (with ambiguity), symbol, comment or status
   text, course, speed and altitude when reported, last heard time, the path of the last packet, packet count, and,
   for objects and items, the **owner** (the source of the last packet that set it). Fields a packet doesn't carry keep
   their last value (a status report doesn't erase the position).
3. Every packet type APRS.NET decodes updates its entry: positions (plain, compressed, Mic-E), objects, items, status
   reports, weather (the position part; readings are F1.10), telemetry (the station only; values are F1.11).
4. **Third-party packets** (`}`) update the entry of the station inside them, not the IGate that wrapped them, with the
   inner packet's path (G06). Until G06 ships, they update nothing and count as packets of the wrapping station.

### Objects and items

5. **Ownership**: an object or item belongs to the station that sent its latest packet. When another station sends the
   same name, ownership moves and the details show the previous owner (F1.6).
6. **Kill**: a killed object or item (`_` flag) is removed at once, whoever sent the kill, and its removal is streamed
   to viewers. A later live packet for the name brings it back.

### Aging and expiry

7. An entry not heard for **30 minutes** is *stale*: the map fades it (F1.4 behavior 19) and lists show it greyed.
8. An entry not heard for **2 hours** expires: the engine removes it and streams the removal. Objects and items expire
   by the same rule (a live object is re-sent by its owner).
9. Both times are settings (Settings › Map › Stations: stale after, remove after, with "never" for removal), per
   station rather than per viewer, because the engine applies them for everyone.
10. Expiry runs on the engine's clock (`TimeProvider`) about once a minute, in one pass, so it costs nothing per
    packet.

### Duplicates

11. A packet that is a **duplicate** (same source, destination and information field within 30 s, path ignored; G05)
    doesn't update entries or counts a second time. On APRS-IS alone this is rare, because the servers already drop
    duplicates; it matters once RF ports join (Phase 3). The packet list (F1.8) still shows it, marked as a duplicate.

### Bounds

12. At most **50,000** entries (an engine option). Beyond that, the least recently heard entry is removed, with its
    removal streamed. A full APRS-IS feed has tens of thousands of stations; a filtered one far fewer.
13. Streaming stays as built (F0.2): a snapshot in chunks of 1,000, then coalesced changes about every 250 ms, with one
    entry per name per batch.

### What the stream carries

14. The map's stream (`WatchStationsAsync`) stays lean: name, kind, position, symbol, last heard and stale. The full
    entry (behavior 2) is fetched on demand with `GetStationAsync(name)` for the details pane (F1.6) and the station
    list (F1.7).

## Service surface

- `StationState` gains `Kind` (station, object, item) and `IsStale`.
- New `Task<StationDetail?> GetStationAsync(string name)`: the full entry (behavior 2), or null when unknown.
- Engine options: `StaleAfter` (30 min), `RemoveAfter` (2 h, or none), `MaxStations` (50,000). The two times become
  station settings in `AppSettings` (behavior 9).

## APRS.NET dependencies

- **G05, duplicate detection**: delivered (`0.2.0-alpha.2`, `DuplicateFilter`, 30 s).
- **G06, third-party payloads** (delivered, `0.2.0-alpha.1`): the inner packet of a `}` payload, as
  `ThirdPartyPayload.Packet` (behavior 4).
- Everything else (positions, objects, items, status, weather, telemetry, Mic-E) is decoded already.

## Desktop vs web differences

None: the store is the engine's, and a gateway's viewers all see its store.

## Acceptance tests

1. A position, then a status report, then another position: one entry with the latest position and the status text.
2. An object from A, then the same name from B: one entry owned by B, previous owner A; a kill from anyone removes it
   and streams the removal; a later live packet restores it.
3. With a fake clock: stale at 30 minutes, removed at 2 hours with the removal streamed; "never" keeps it.
4. At the entry cap, the least recently heard entry is removed first.
5. The same packet via two paths within 30 s updates once; after 30 s it updates again.
6. After G06: a `}` packet updates the inner station with the inner path, not the IGate.
7. `GetStationAsync` returns the full entry over the gateway (JSON round trip without reflection), and null for an
   unknown name.

## Decisions for review

1. **Default times**: stale after 30 minutes and removed after 2 hours (proposed), matching a typical beacon interval of
   10–30 minutes. Some operators prefer longer for sparse areas, which is why they're settings.
2. **Kill from a non-owner removes the object** (behavior 6). Proposed: yes, because the APRS-IS sees no owner
   authority; the details show who killed it.
