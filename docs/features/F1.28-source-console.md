# F1.28 Source console

Status: spec'd for 0.5.0 ([#246](https://github.com/APRS-NET/AprsMap/issues/246); maintainer request, 2026-10-18).
Waits on G33 ([APRS.NET#262](https://github.com/APRS-NET/APRS.NET/issues/262)); the command line (behaviors 9, 10) waits
on G14's typing over an open connection ([APRS.NET#249](https://github.com/APRS-NET/APRS.NET/issues/249)).

## User story

As an operator setting up or troubleshooting a TNC or an APRS-IS connection, I can watch everything that source sends
and receives, including what never becomes a packet, and type to a TNC, so I can see why nothing is coming through
without reaching for another program.

## Background

- The packet list (F1.8) shows packets: what decoded. A TNC sending text, frames that aren't APRS, frames for another
  port, frames dropped as corrupt, KISS commands, the steps of switching a radio into KISS (F3.2) and what the station
  sent are invisible today; APRS.NET only counts some of them.
- The dashboard (F1.22) and the pills (F1.25, F3.1 behavior 13) say a source's state and warnings, not its traffic.
- F1.27 records unexpected packets for the test corpus. This is the live view, for the operator.

## Behavior

### Watching

1. A **Source console** panel (a dockable panel, F1.0; app menu › Panels, and **Console…** on every source pill's menu,
   which opens it on that source) shows one source at a time, picked from the active profile's sources.
2. Each line is one entry from APRS.NET's traffic event:
   1. the time (to the millisecond, in the clock setting of F1.8), the direction (in, out), and the kind in words:
      packet, not APRS, other port, KISS command, dropped frame (with why: bad escape, too long), unframed (text or
      noise), sent, typed (a command or bytes sent from the command line), and the setup steps (sent, received,
      failed);
   2. the content: for a frame, the packet as TNC-2 text when it decoded, otherwise the AX.25 header in words and the
      bytes in hex; for unframed bytes, the line as text when it looks like text, otherwise hex; for APRS-IS, the line.
   Unframed text comes a line at a time; a prompt without a line end (`cmd:`) stays on its line and the next text is
   added to it, so a TNC's prompt and the command typed after it read as they would in a terminal.
   The kinds have their own icon and colour from the theme (quiet for packets, the warning colour for dropped and
   failed), never colour alone.
3. **Hex** shows any line's bytes as hex and characters side by side. **Copy** copies the lines shown (or the chosen
   ones) as text with times, ready for an issue.
4. The console shows the **last 500 entries** of the source, and keeps up as new ones come. Scrolling up pauses it, as
   the packet list does (F1.8 behavior 6): new entries are counted ("12 new") until it's scrolled back to the top.
5. **Filter** by kind: everything (the default), problems only (not APRS, other port, dropped, unframed, setup failed),
   or packets only. A text box filters on the content.
6. For APRS-IS, the login line shows with the passcode masked by APRS.NET (`pass ****`); server comments, keepalives,
   the login answer, `#filter` commands and sent packets each have a line.

### Recording

7. The engine keeps the last 500 entries of each **KISS and APRS-mode source** from the moment it opens, so the console
   shows what happened at connect even when opened later. For **APRS-IS**, whose feed can be hundreds of lines a
   minute that the packet list already shows, entries are kept only while a console is watching it, from then on.
8. Nothing is written to disk. Closing the app or switching profiles clears it.

### Typing to a TNC

9. For a serial KISS source, the console has a **command line** (F3.2 behaviors 8–11): Enter KISS, Leave KISS, a line to
   type and a Bytes choice. Opening it puts the source in manual mode; the answer shows in the console as unframed
   lines. It isn't offered for APRS-IS, KISS over TCP (Direwolf has no prompt) or APRS-mode sources (receive only).
10. Typed commands need a licensed profile without Disable TX, and the line says "Some commands make the radio transmit"
    above it (F3.2 behavior 11).

### On a gateway

11. The console is the operator's: it shows login lines, filters and what the radio sends, so watching is operator only
    (`gateway.operator-only`, F2.9's signed-in operator once built), and so is the command line.

## Service surface

- `IEngineService.WatchSourceTrafficAsync(sourceId)` → `IAsyncEnumerable<TrafficEntry>`: the kept entries first, then
  new ones as they come; ending when the source is removed. Watching an APRS-IS source starts keeping its entries
  (behavior 7).
- `TrafficEntry` (Contracts): `At`, `SourceId`, `Direction` (`In`, `Out`), `Kind` (`TrafficKind`, mirroring APRS.NET's
  kinds, `RawSent` included, plus the APRS-IS line kinds), `EndsLine`, `Text` (the TNC-2 text, line or header in words, or null), `Bytes` (at most 1,024,
  then marked cut), `Port`, `Detail` (why a frame was dropped, a setup step's text).
- The command line uses F3.2's `SetTncManualAsync` and `SendTncCommandAsync`.
- Error codes: `console.source-unknown`.

## APRS.NET dependencies

- **G33** ([APRS.NET#262](https://github.com/APRS-NET/APRS.NET/issues/262)): the `Traffic` events on KISS and APRS-IS
  connections, with stable kinds and the passcode masked. KISS half in APRS.NET#263 (in review); APRS-IS still to do. Raised on APRS.NET's threads with no history, so the engine
  keeps the ring buffers (behavior 7) and the view marshals to the UI thread.
- **G14** ([APRS.NET#249](https://github.com/APRS-NET/APRS.NET/issues/249)) part 3: manual mode and sending over an open
  connection, for behaviors 9 and 10 (APRS.NET#264, in review, stacked on #263).

## Desktop vs web differences

| | Desktop | Web (gateway) |
| --- | --- | --- |
| Who can watch | The user | The operator only |
| Command line | A licensed profile | The operator, with a licensed profile |
| Entries | In the engine, in this process | In the gateway, streamed over SignalR |

## Acceptance tests

1. A fake TNC that sends text, a frame with a bad escape, a too-long frame, a non-APRS frame, a frame for another port,
   a command frame and a good frame gives one console line of each kind, in order, the text as lines.
2. Opening the console a minute after a KISS source connected shows the entries from its connect.
3. An APRS-IS source's login line shows with the passcode masked; nothing is kept for it until a console watches.
4. With 600 entries, the console holds the last 500; scrolling up pauses it and counts new entries; back at the top it
   catches up.
5. Problems only hides packets and sent lines; Copy gives the lines shown with times.
6. A sent position shows as an out line with its TNC-2 text.
7. On a gateway, a viewer's `WatchSourceTrafficAsync` is refused with `gateway.operator-only`.
8. The panel passes the accessibility checks (F0.6): kinds have names for screen readers, it works at 200 % text and in
   high contrast.

## Decisions for review

1. **500 entries a source** (proposed): enough for a connect and some minutes of RF; a few hundred KB at most.
2. **KISS sources always kept, APRS-IS only while watched** (proposed): RF is slow and the connect is the interesting
   part; APRS-IS is fast and its packets are in the packet list already.
3. **Nothing written to disk** (proposed): F1.27 records for the corpus; Copy covers sharing.
4. **Operator only on a gateway** (proposed), even with the passcode masked: it shows the station's filter and setup.
5. **No command line for KISS over TCP** (proposed): Direwolf and soundmodem have no command prompt over KISS.
