# F1.0 Shell and docking

Status: building ([#64](https://github.com/APRS-NET/AprsMap/issues/64))

Built: the shell with the default layout, docking, floating (OS windows on the desktop, in the page on the web), tabs
that wrap, theme and text size, saving and restoring per viewer, the format version and panel changes, an unreadable
layout set aside with a notice, `--reset-layout`, the placement check for floating windows and the main window, the
check again when monitors change, and the trimming allowance for Dock (behaviors 1–3, 5, 6, 8–13, 15). Still to
build: the keyboard panel menu (Move to), the app menu (Reset layout, Gather windows, reopen closed panels), Ctrl+Tab,
the narrow-window layout and the browser smoke test in CI (behaviors 4, 7, 14).

## User story

As an operator, I arrange the app my way: the map in the middle and panels (packets, station details, later messages
and conversations) docked around it, tabbed together, split, hidden at the side, or floated. On the desktop a panel can
go to its own window on another monitor. The app reopens as I left it, and never leaves a window somewhere I can't
reach it.

## Behavior

### Panels

1. The window has a fixed centre, the **map** (F1.4), and **panels** docked around it. Phase 1 panels: Packets (F1.8),
   Details (F1.6), Stations (F1.7) and extra map views (F1.16). Messages and one panel per conversation come with
   Phase 2 (F2.4), and several conversations can be open at once.
2. **Default layout:** Stations on the left, Details on the right, Packets along the bottom.
3. A panel can be dragged to dock on any side of another, tabbed with it, split, set to auto-hide at the window edge,
   or floated. The map can't be closed or floated.
4. **Without dragging:** each panel's menu (reachable with Tab, and opened with Enter) offers **Move to left / right /
   bottom**, **Float**, **Auto-hide** and **Close**. **Ctrl+Tab** switches between panels. Closed panels are reopened
   from the app menu.
5. **Floating:** on the desktop, a floated panel is its own OS window, placed next to where it was docked. In the
   browser it floats inside the page.
6. Panel tabs wrap onto another row rather than running off the panel. Docking chrome follows the theme, palette,
   density and text size like every other control (F0.6), and its text is translated (F0.9).
7. **Narrow windows** (below the shell's narrow breakpoint, UX doc) use the fixed responsive layout instead. The saved
   layout is kept and comes back when the window is wide again.

### Saving

8. The layout saves automatically, per viewer, when it changes and when the app closes:
   - **desktop:** a `layout.json` in the settings folder, next to the appearance preferences;
   - **web:** browser storage.

   It isn't part of the station's settings (F0.4), so on a gateway every viewer has their own.
9. Only the arrangement is saved (panel ids, docks, sizes, floating windows' positions and sizes). Panel content
   always comes from the engine.
10. **Reset layout** (app menu, and the `--reset-layout` start-up option on the desktop) restores the default. A
    layout that can't be read is moved aside, the default is used, and the app says so once.
11. The saved layout carries a format version. A panel that no longer exists is dropped; a new panel appears in its
    default place.

### Windows that stay reachable

12. Before any saved floating window opens, its position is checked against the screens that exist now. If too little
    of its title bar would be in a screen's usable area, it moves to the nearest screen, and shrinks to fit when it's
    larger than that screen.
13. The same check runs on open windows when monitors are added or removed while the app runs.
14. **Gather windows** (app menu) moves every floating window onto the main window's screen.
15. The main window gets the same check for its own saved position and size.

## Service surface

None. The layout is per-viewer UI state, like appearance (F0.6), stored through `IPreferenceStore`. The browser and
the desktop work identically apart from floating (behavior 5).

## APRS.NET dependencies

None.

## Implementation notes

- **Docking library:** Dock (MIT, `Dock.Avalonia`, `Dock.Model.Mvvm`, `Dock.Avalonia.Themes.Fluent`,
  `Dock.Serializer.SystemTextJson` with its source generator), from the [docking spike](../spikes/docking.md). Only
  `AprsMap.UI/Shell` references it.
  - The placement check (`WindowPlacement`) and the saved-layout format stay our own, so Dock could be replaced
    by rewriting the shell alone.
  - Dock updates come through Dependabot and are reviewed like any dependency.
- **Theme:** Dock's semantic tokens are mapped onto ours (`Themes/DockTokens.axaml`). Its fixed sizes
  (`DockFontSizeNormal`, tab, header and button sizes) are set from the text scale by `AppearanceService`.
- **Browser:** `DockSettings.UseManagedWindows` is on, so floating windows, drag previews and dock targets stay in the
  page.
- **Trimming:** Dock's themes use 13 reflection bindings. The browser publish allows the library trim summary warning
  (`IL2104`) for the Dock assemblies only, named in the project. Any other library producing trim warnings still fails
  the build, and our own code's trim warnings stay errors.
  - A browser smoke test covers what those bindings drive: open the app, drag a splitter, drag a tab to another dock,
    float a panel.
  - We offer Dock an upstream change to compiled bindings and remove the exception once it ships.

## Desktop vs web differences

| | Desktop | Web |
| --- | --- | --- |
| Floating panel | OS window, any monitor | Inside the page |
| Saved in | `layout.json` in the settings folder | Browser storage |
| Reset at start-up | `--reset-layout` | Reset layout in the menu |
| A panel in its own browser tab | — | Later: F1.24 |

## Acceptance tests

1. The default layout shows the map, Stations, Details and Packets; the map can't be closed or floated.
2. Each panel can be moved, floated, auto-hidden and closed from its menu by keyboard alone; Ctrl+Tab cycles panels.
3. A changed layout, including a floating panel, survives a restart; Reset layout restores the default; an unreadable
   file is moved aside.
4. Placement, as unit tests:
   - a window on a monitor that's gone moves to the nearest screen;
   - a window at negative coordinates comes back;
   - a title bar above the screen is brought down;
   - an oversized window shrinks;
   - mixed scaling works;
   - a window on a screen that still exists stays where it was.
5. Every palette and theme at 200 % text: docking chrome follows tokens and no tab or title runs off (the existing
   render check).
6. Browser smoke test (published, trimmed, headless Firefox): splitter drag, tab move and in-page float work, with no
   console errors.
7. A narrow window shows the responsive layout; widening it restores the saved one.
