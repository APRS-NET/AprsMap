# F0.9 Ready for translation

Status: built (English only): engine errors as codes, UI text in resource files with a live language switch, the
pseudo-language and CI guards, the language picker in Settings › Appearance, and [translating.md](../translating.md).
Still open: the packet list's summaries come from the engine in English (behavior 16), and the per-language
completeness report comes with the first translation (behavior 20).

## User story

As a user whose first language isn't English, I can use the app in my language once someone has translated it, and
switch language without restarting. As a translator, I can translate it without reading code. As a contributor, I can't
add English text to a screen by accident.

This feature builds the groundwork only: English, plus a pseudo-language for testing. Real translations arrive later,
from contributors, without code changes.

## Behavior

### Where text lives

1. Every user-visible string in `AprsMap.UI` comes from resource files: `Strings.resx` (English, the fallback) and
   `Strings.<culture>.resx` for each translation, compiled into satellite assemblies. No view or view model holds
   literal user-visible text. Exceptions: callsigns, station names, packet content and other data, and symbols such as
   `·` or `…` used as separators. Separators belong inside the translated string, because their position varies by
   language.
2. Keys are dotted and grouped by screen (`Status.Connected`, `Wizard.Callsign.Title`). Each key has a resx comment for
   translators saying where it appears and what each placeholder holds.
3. A string that names the product takes `Brand.DisplayName` as a placeholder (`{product}`), never the literal name,
   so renaming the product (`tools/rename-product.py`) keeps working in every language.
4. Strings with counts or choices use ICU MessageFormat (`{count, plural, one {# packet} other {# packets}}`), because
   plural rules differ by language. The formatter is the `MessageFormat` package (Jeffijoe.MessageFormat, MIT), which
   passed the browser publish trim check and adds 17 KB (Brotli). It writes `#` as a bare number, so the localizer points
   each `#` at the number formatted for the culture (`1,234`; `1.234` in German) and the plural form is still chosen
   from the number.

### Choosing the language

5. By default the app uses the OS language on desktop and the browser's language (`navigator.languages`) on the web,
   falling back along the culture chain (`de-AT` → `de` → English).
6. Settings → Appearance has a Language list: "System default", then each language that has a translation, each shown
   in its own name (`Deutsch`, `Français`; from `CultureInfo.NativeName`). The pseudo-language appears only in debug
   builds or when `Ui:ShowPseudoLanguage` is set.
7. The choice is per viewer, stored with the appearance settings (F0.6): in the user's settings folder on desktop and in
   browser storage on the web. It is never part of the station's `AppSettings`, so on a gateway each viewer picks their
   own and nobody changes it for others.
8. Changing language takes effect at once, without a restart: every bound string updates, and open dialogs keep their
   state.
9. Numbers, dates, times and units are formatted with the chosen culture (decimal separator, digit grouping, 24-hour
   or 12-hour clock). Callsigns, raw packets, Maidenhead locators and coordinates typed in APRS formats are never
   localized.
10. The UI language is what the engine receives where the language matters, such as the `language` argument of
    `GeocodeAsync` (F0.5).

### The engine sends codes, not English

11. On the web the engine runs on the gateway, which can't know each viewer's language, so the engine never produces
    user-facing sentences. Anything it reports to a user is an `EngineError` (in Contracts):
    `EngineError(string Code, string Message, IReadOnlyDictionary<string, string>? Args)`:
    - `Code` is stable, for example `settings.profile.name-duplicate`;
    - `Message` is English, for logs and for a client too old to know the code;
    - `Args` are the values to fill in, for example `{ "profile": "Portable" }`.
12. Errors keep their current exception types, so existing callers keep working. Each type gains the error:
    - `EngineArgumentException : ArgumentException` for invalid settings and callsigns;
    - `EngineOperationException : InvalidOperationException` for lookup failures;
    - `EngineAccessException : UnauthorizedAccessException` for operator-only calls.

    Each one has an `EngineError` property (interface `IHasEngineError`).
13. Over SignalR the gateway sends the error as JSON inside the `HubException` message. The remote client turns it back
    into the same exception type and `EngineError`. This replaces matching English text such as `OperatorOnlyMessage`.
14. The UI shows `Strings["Error." + Code]` filled from `Args`. For an unknown code it shows `Message`, so a newer
    gateway's new errors still read sensibly in an older browser tab.
15. The codes (`EngineErrorCodes` in Contracts) cover everything the engine reports today:
    - settings validation: `settings.incomplete`, `settings.profile.id-duplicate`, `…name-missing`,
      `…name-duplicate`, `…position-off-globe`, `…position-incomplete`, `settings.active-profile-missing`;
    - APRS.NET's validation codes as `aprs.<code in kebab case>` (for example `aprs.callsign-invalid-character`), with
      the profile, field, value, character position and character as arguments; `settings.invalid` for a check APRS.NET
      doesn't code;
    - gateway gates: `gateway.settings-read-only`, `gateway.operator-only`;
    - address lookup: `geocoding.disabled`, `…refused`, `…superseded`, `…unreachable`, `…http-error` (with the status),
      `…unreadable`.

    The exception type follows from the code's prefix (`gateway.` → access, `geocoding.` → operation, anything else →
    argument), so the in-process engine and the remote client always throw the same type.
16. Packet summaries (`PacketView.Summary`, now English sentences from `PacketSummarizer`) become structured: the
    packet kind, position, symbol code and comment as fields. The UI writes the sentence. Comments and other packet
    text are shown as sent.
17. Symbol names (for example "car") come from APRS.NET's symbol table in English. They are looked up in UI resources
    by symbol code when a translation has them, and fall back to English otherwise.

### Testing and keeping it clean

18. **Pseudo-language** `qps-ploc` (the culture name Windows uses for pseudo-localization), generated at build time
    from `Strings.resx`. It adds accents (`Ŝţåŕţîñĝ`), lengthens each string by about 40 %, and wraps it in brackets.
    Headless UI tests render every screen in it. Text in plain English shows a missed string, and a missing closing
    bracket shows clipping.
19. **Guards in CI**:
    - a test fails when a view has a literal `Text`, `Content`, `Header`, `Watermark` or `ToolTip.Tip` value, or a
      `Run` with literal text (separators excepted);
    - a test fails when a key is used in code but missing from `Strings.resx`, or when a placeholder in a translation
      doesn't match the English;
    - a test checks that every `EngineError` code has an `Error.*` string.
20. A translation file may be incomplete. Missing keys fall back to English at runtime, and the build reports each
    language's percentage.

### Layout

21. Layouts allow text about 40 % longer than English (the pseudo-language checks this), on top of the 200 % text-size
    requirement (F0.6).
22. Views use start/end alignment and margins, not left/right, so right-to-left languages can work later. Full
    right-to-left support (mirroring, bidirectional text checks) is out of scope here. It is scoped when a right-to-left
    translation is offered.

### Web build

23. The browser build ships the globalization data and satellite assemblies for the shipped languages. It loads only
    the chosen language's data. The publish's size change is measured and recorded, as in the spikes.
24. **Fonts.** The browser has no system fonts, so the app bundles them. Latin, Greek and Cyrillic come with the base
    font. Scripts with large fonts (Chinese, Japanese, Korean; Arabic and Hebrew with right-to-left) load their font
    only when that language is chosen. Adding such a language is gated on this, and it is out of scope until one is
    offered.

### Translation workflow

25. Translations are contributed as pull requests to the `.resx` files, directly or through hosted Weblate (free for
    open-source projects), which writes resx and opens pull requests. The choice of service is a maintainer decision.
26. `docs/translating.md` explains it: the glossary, placeholders and plurals, how to test with the pseudo-language,
    and the clean-room rule. Translations are our own work; never copy another APRS program's translations, especially
    APRSIS32's.
27. A glossary fixes how APRS terms are treated. Callsign, SSID, beacon, digipeater, IGate, APRS-IS, passcode and Mic-E
    are kept or translated as the glossary says per language. The glossary starts with English definitions.

## Service surface

- Added to Contracts: `EngineError`, the three exception types (behavior 12), and `EngineErrorCodes` (string
  constants).
- Changed: `PacketView` gains structured summary fields (behavior 16). `Summary` stays for one release as the English
  fallback, then is removed.
- Unchanged: every `IEngineService` signature. Only the exceptions carry more.

## APRS.NET dependencies

- **G27, validation errors with codes**: delivered in APRS.NET `0.1.0-alpha.15`. `AprsValidationException` carries an
  `AprsValidationErrorCode` (callsign length, character or SSID; server host or port; filter; path), plus the offending
  value and position. The engine maps each code to an `EngineError` code with those values as `Args`, so the wizard can
  say what is wrong and where. Server strings are parsed with `AprsIsEndpoint.Parse`, which throws the same codes,
  instead of `TryParse` and a message of our own.
- Parsing already has codes (`ParseIssue`, `MaidenheadParseError.Kind`/`Part`), and the UI uses those directly.

## Acceptance tests

1. Rendering the main view and every wizard step in `qps-ploc` shows no unbracketed text and no clipped brackets
   (headless).
2. The guard tests fail on a view with `Text="packets"`, a missing key, and a placeholder mismatch.
3. Switching from English to `qps-ploc` and back updates the status bar and an open dialog without losing its input.
4. With `de-AT` requested and only `de` shipped, German is used; with only English shipped, English.
5. A gateway rejecting a duplicate profile name sends `settings.profile.name-duplicate` with the profile name. The
   remote client raises `EngineArgumentException` with that code. The UI shows the resource string with the name
   filled in.
6. An unknown code from the gateway shows its English `Message`.
7. On a read-only gateway, `GeocodeAsync` raises `EngineAccessException` with `gateway.operator-only`, and no English
   text is compared anywhere.
8. Plural strings give "1 packet" and "2 packets" in English, and the right forms in the pseudo-language.
9. The browser publish passes the trim check with the formatter and satellite assemblies, and its size change is
   recorded.
