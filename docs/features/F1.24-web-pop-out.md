# F1.24 Web pop-out panels

Status: built for 0.7.0 ([#212](https://github.com/APRS-NET/AprsMap/issues/212)); decisions proposed 2026-10-26 for the
maintainer's review.

## User story

As someone watching the station in a browser, I can take a panel, such as the packet list or Details, out into a tab
or window of its own and put it on my second monitor, while the map stays full-size in the first. Selecting a station
in either selects it in both.

## Background: what already exists

- The browser app (F1.14) runs the same UI as the desktop over the gateway's SignalR hub; its panels can float inside
  the page (managed windows), not outside it, since a browser page can't open native windows.
- The gateway counts each browser as a viewer up to its limit (F1.14 behavior 3).

## Behavior

1. **Open in a new tab** is on each panel's menu in the browser (not on the desktop, whose panels already float into
   windows of their own). It opens the same page with `?panel=<kind>` in a new tab, which the browser may show as a
   window; the user can drag it to another monitor.
2. **A popped-out tab shows that panel alone**, filling the page: no map, no other docks, and it can't be closed,
   floated or moved, since there's nowhere else for it to go. Its tab title names the panel first ("Packets · NZ0P-10 ·
   …"). It doesn't load or save the layout: the tab it came from keeps that. Menus and settings work as in any tab.
   Opening the same address directly does the same, so a bookmark can open a panel on its own.
3. **The selection is shared** between the app's tabs in that browser: selecting a station in one selects it in the
   others, so Details in a popped-out tab follows the map in the first. It uses the browser's `BroadcastChannel`, which
   stays within the browser and the gateway's address; nothing goes through the gateway.
4. **Each tab is a viewer** (proposed): it has its own connection to the gateway and its own streams, so it counts
   towards the gateway's viewer limit like any browser (F1.14 behavior 3). A full gateway says so in the new tab, and
   the tab it came from carries on.

## Service surface

None new on `IEngineService`. In the UI: `PlatformServices.PopOutPanel`, `OpenPopOut` and `SelectionChannel`
(`ISelectionChannel`: `Publish`, `Received`), set only by the browser app.

## APRS.NET dependencies

None.

## Desktop vs web differences

Browser only. The desktop's panels already float into windows of their own (F1.0).

## Acceptance tests

1. With a pop-out opener, a panel's menu offers Open in a new tab and it asks for that panel; without one (the
   desktop) it isn't offered.
2. A tab started for a panel shows it alone, not closable, and doesn't save a layout; its title names the panel.
3. A selection in one tab is sent to the others, and one received is shown without being sent back.
4. In a browser (headless), `?panel=Packets` starts the app with the packet list alone.

## Decisions for review

1. **Tabs, not in-page windows** (proposed): a tab can go to another monitor; in-page windows already exist.
2. **Each tab counts as a viewer** (proposed): it's a full connection. Letting a tab ride on another's slot would need
   the gateway to tie the two together, which can come later if limits are tight.
3. **Only the selection is shared** (proposed): the View filter, range and layout stay each tab's own, as they are
   per viewer already.
