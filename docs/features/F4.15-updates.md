# F4.15 Updates

Status: draft ([#186](https://github.com/APRS-NET/AprsMap/issues/186), milestone 0.5.0-alpha.1). A maintainer request
(2026-10-16): the app should find new releases itself and, on desktop, install them.

## User story

As a desktop user, I hear about a new release from the app itself, read what changed, and install it with one click
without losing my settings. As a gateway operator, I'm told a new image is out and how to pull it; my viewers aren't.
As anyone, I can turn the check off, and it never sends anything about me or my station.

## Behavior

### The check

1. The engine checks for a newer release **a minute after it starts and then every 24 hours** while it runs, and when
   **Check now** is pressed (Settings › About). The last check's time and result are kept with the settings, so a
   restart within 24 hours doesn't check again.
2. The check is **one anonymous HTTPS request** to the GitHub releases API for the repository in `Brand.SourceUrl`
   (`GET /repos/{owner}/{repo}/releases?per_page=20`), with a `User-Agent` of the product slug and version and the last
   answer's `ETag` (`If-None-Match`, so an unchanged list costs nothing against GitHub's limits). No callsign,
   location, settings or identifier is sent, and nothing else is fetched until the user asks to install.
3. A release counts when it is **published** (not a draft), its tag is `v` and a SemVer 2.0 version, the version is
   **newer than the running one** by SemVer precedence, it is on the user's **channel** (behavior 5), and it is
   **ready for this install** (behavior 4). The newest such release is the update; older ones are covered by its
   notes.
4. **Ready** means its files are attached, since the release workflow uploads them some minutes after the tag:
   1. a desktop archive build needs the archive for its own runtime (`aprsmap-v…-linux-x64.tar.gz` and so on);
   2. an installed desktop build needs the Velopack feed for its own channel (`releases.<channel>.json`, behavior 12);
   3. a gateway needs the image marker `aprsmap-v…-image.txt`, which the release workflow attaches after it pushes
      the container (it holds the image's tags and digest).
   File names use `Brand.Slug`, never a literal name.
5. **Channels**: **Pre-releases** (every alpha, beta or rc, and stable) or **Stable** (versions without a pre-release
   part). Until 1.0 every release is a pre-release, so a pre-release build defaults to Pre-releases and a stable build
   to Stable. Moving from Pre-releases to Stable never offers an older version: the user stays where they are until a
   stable version is newer.
6. The setting **Check for updates** (on by default) turns the check off; with it off no request is made at all, and
   Check now still works when pressed. **`Engine__Updates__Check=false`** (environment or `appsettings.json`) turns
   it off where the engine starts and hides Check now, for networks that block the internet or for packagers whose
   own store updates the app (behavior 17).
7. A failed check (no network, GitHub down, rate limited) is quiet: About says "Couldn't check for updates: <reason>"
   with the time, and the next check is at the usual time. It never shows a notice or a dialog.

### The notice

8. An update shows a **quiet notice in the status bar**, "Update available: 0.4.0-alpha.2", in the normal text colour
   with an info icon (theme tokens only), never a pop-up or a modal at start. It is reachable by keyboard and read by
   a screen reader once, when it appears.
9. Opening it shows a small dialog:
   1. the version and its date, with the release's notes as plain text (headings, lists and links kept as text, the
      first 40 lines and a **Release notes** link to the release page for the rest);
   2. **Update and restart** when this build can install it (behavior 11), otherwise **Download**, which opens the
      release page in the browser;
   3. **Skip this version**, which hides the notice until a newer version comes out;
   4. **Later**, which hides it until the next start.
10. Settings › About shows the running version, the channel, the last check and its result, Check now, and the
    update's version with the same actions when there is one.

### Installing on desktop (Velopack)

11. **Installed builds** (from the Setup.exe, the macOS package or the AppImage, behavior 12) install updates in the
    app. **Update and restart**:
    1. downloads the update in the background (a delta package from the running version when there is one, otherwise
       the full package), with progress in the notice and Cancel;
    2. checks the package's SHA-256 against the feed before using it;
    3. when it's downloaded, offers **Restart now** or applies it **the next time the app is closed**, so it never
       interrupts a session by itself;
    4. on restart, the app reopens on the new version with its layout and settings.
    Archive builds can't update in place (they may be anywhere, read only or shared), so they only show **Download**.
12. **The release workflow** also builds Velopack packages with `vpk pack`, each on its own platform's runner, and
    attaches them to the same GitHub release:
    1. Windows x64 and arm64: `Setup.exe`, full and delta `.nupkg` packages and `releases.win-<arch>.json`;
    2. macOS x64 and arm64: an `.app` bundle in a `.pkg`, with its packages and feed;
    3. Linux x64 and arm64: an `.AppImage`, with its packages and feed.
    The package id is `Brand.Slug`, the channel is the runtime id, and the previous release's packages are fetched
    first so deltas can be made. The archives stay as they are.
13. **Settings are kept.** Settings, preferences, layouts and the tile cache live in the user's settings folder (F0.4),
    never beside the program, so an update, a move from an archive to an installed build, or an uninstall leaves them
    alone. Uninstalling says so and points to Start over (F0.10) for removing them.
14. **Signing** comes when the code-signing account is approved (F4.8): the release workflow signs the Windows program
    and Setup.exe through the signing service before packing, and the feed is unchanged. Until then the packages are
    unsigned: Windows SmartScreen warns on the first install (not on updates, which the app applies itself), and macOS
    needs the usual right-click Open for an app without a Developer ID. The deployment guide says so.

### The gateway

15. A gateway never updates itself. The engine checks as on desktop (behavior 4.3 decides when a release is ready) and
    **only the operator** sees the notice: today a connection allowed to change settings (`AllowSettingsChanges`),
    and the operator port once F1.26 is built. Viewers get no notice, and the update isn't in anything sent to them.
16. The operator's dialog has no install button. It shows the version, the notes, the image tag
    (`ghcr.io/…:<version>`, from the image marker) and how to update: `docker compose pull && docker compose up -d`,
    Watchtower, or Unraid's Check for updates, with a link to the deployment guide's section on updating.

### Packaged elsewhere

17. Later, the app is also offered through **winget**, **Homebrew** and **Flathub**, which update it themselves. Those
    builds are made with `Engine__Updates__Check=false` set in their `appsettings.json` and say "Updates come from
    <store>" in About, so two updaters never compete.

## Service surface

- `UpdateSettings(bool Check = true, UpdateChannel? Channel = null, string? SkippedVersion = null)` in `AppSettings`
  (`Updates`); `UpdateChannel`: `PreReleases`, `Stable`; null means the default of behavior 5.
- `UpdateInfo(string Version, DateTimeOffset Published, Uri ReleasePage, string Notes, string? ImageTag,
  IReadOnlyList<UpdateFile> Files)` and `UpdateFile(string Name, Uri Url, long Size)`.
- `UpdateStatus(DateTimeOffset? LastChecked, EngineError? LastError, UpdateInfo? Update, bool CheckDisabled)`.
- `Task<UpdateStatus> GetUpdateStatusAsync()`, `Task<UpdateStatus> CheckForUpdateAsync()` and
  `IAsyncEnumerable<UpdateStatus> WatchUpdateStatusAsync()`: operator-only on a gateway (`gateway.operator-only`).
  `SkipUpdateAsync(string version)` saves `SkippedVersion`.
- Error codes: `updates.unreachable`, `updates.rate-limited`, `updates.unexpected-answer`.
- In the UI, `PlatformServices` gains `IAppInstaller` (`CanInstall`, `DownloadAsync(UpdateInfo, IProgress<double>,
  CancellationToken)`, `ApplyOnExit()`, `RestartNow()`), implemented in `AprsMap.Desktop` with Velopack and absent in
  the browser. The engine knows nothing of Velopack; the installer takes the `UpdateInfo` the engine found.
- The ready check of behavior 4 needs to know how the engine is running: `EngineOptions.Updates.Kind` is `Archive`,
  `Installed` (set by the desktop host when Velopack says it's installed) or `Gateway`, with the runtime id.

## APRS.NET dependencies

None: this is the app's own release feed, not APRS. The check uses `HttpClient` and `TimeProvider` in `AprsMap.Core`
(MIT); Velopack (MIT) is referenced only by `AprsMap.Desktop`.

## Desktop vs web differences

| | Desktop | Web (gateway) |
| --- | --- | --- |
| Who sees the notice | The user | The operator only |
| Install | Update and restart (installed builds), Download (archives) | None: pull the new image |
| Ready when | Its archive or its Velopack feed is attached | The image marker is attached |
| Turning it off | Settings, or `Engine:Updates:Check` in `appsettings.json` | Settings (operator), or `Engine__Updates__Check` |

## Acceptance tests

1. Against a fake releases API: a newer published pre-release is offered on Pre-releases and not on Stable; a draft,
   an older version, a bad tag and a release without this install's file aren't; `0.4.0-alpha.10` is newer than
   `0.4.0-alpha.9`, and `0.4.0` newer than `0.4.0-rc.1`.
2. The request carries the `User-Agent` and `If-None-Match`, and nothing else from the settings; a 304 keeps the last
   answer.
3. The schedule: a check one minute after start and every 24 hours on a fake `TimeProvider`; none at start when the
   last one is under 24 hours old; none at all with Check for updates off, or with `Engine__Updates__Check=false`
   (and Check now is hidden then).
4. A failed check, a 403 with the rate-limit headers and a malformed answer each set `LastError` and show nothing in
   the status bar.
5. The notice appears in the status bar, opens its dialog, Skip this version hides it until a newer one, and Later
   until the next start; it works by keyboard, is announced once, and fits at 200 % text in every theme.
6. A gateway connection that may not change settings gets `gateway.operator-only` from the update calls and no
   notice; an operator gets the notice with the image tag and no install button.
7. Desktop: the installer downloads a package whose hash doesn't match the feed and refuses it; a matching one is
   applied on Restart now and on the next close.
8. The release workflow attaches, for each runtime, the archive, the Velopack packages and feed, and the image marker;
   a dry run on a fork makes a delta from the previous release.
9. Manual, on the test bed: install 0.5.0-alpha.1 from Setup.exe on Windows, the `.pkg` on macOS and the AppImage on
   Linux, publish a test release on a fork, and update each in place with its settings and layout kept.

## Decisions for review

1. **The check is in the engine** (proposed), so the gateway and the desktop share one check and parity holds; the
   installer is a desktop platform service. The alternative, Velopack's own GitHub check, works only in installed
   builds and can't tell a gateway operator anything.
2. **On by default** (proposed), with the request described in About and the deployment guide. It sends nothing but
   the version in the User-Agent; the alternative is asking in the setup wizard.
3. **Daily, and a minute after start** (proposed), so start-up isn't slowed and GitHub's anonymous limit (60 an hour
   per address) is never near.
4. **Download on request, apply on restart** (proposed), not a silent background download: it uses a metered
   connection only when asked, and the user knows what's coming. A setting for automatic downloads can come later.
5. **Two channels** (proposed): Pre-releases and Stable, defaulting from the running build; no separate beta channel
   until there are betas.
6. **Archive builds keep only Download** (proposed): they can be anywhere, and replacing files in place isn't safe.
   The deployment guide recommends the installed builds for most users once they exist.
7. **An image marker asset** (proposed) tells the gateway the image is pushed, rather than querying the container
   registry, which needs a token and a second API.
8. **Unsigned packages ship before signing** (proposed), as the archives do now, so the update path can be tested
   early; signing is added to the same workflow when the account is approved.
