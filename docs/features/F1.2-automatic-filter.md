# F1.2 Automatic filter

Status: draft

## User story

As an operator, APRS-IS sends me the stations I'm looking at: around my location by default, and wherever I pan the
map, plus any station I'm following, without my writing filter syntax. If I do know filter syntax, I can add my own
parts. I can see on the map what the filter covers.

Built already: a profile's own filter is sent as typed; without one, a fixed stand-in of 150 km around the profile's
location, written with APRS.NET's filter terms (G04). F1.1 adds changing the filter without a new login (`SetFilterAsync`).

## Behavior

### The parts

1. The engine builds the APRS-IS filter from parts, with APRS.NET's typed filter builder (G04):
   1. **My range**: a range around my location (F1.13), with the profile's **range** setting (default 150 km; 0 means
      no range part, as an IGate wants);
   2. **Map view**: when the map shows an area outside my range, a range around the view's centre covering the view
      (radius: half the view's diagonal), capped at 1,000 km. Zoomed out wider than that, no map part is added;
   3. **Followed station**: while the map follows a station (F1.7), a friend range around it (`f/CALL/km`) with the
      same radius as my range;
   4. **Tracked stations**: stations pinned to extra map views (F1.16) as a buddy list (`b/CALL1/CALL2…`);
   5. **The profile's own filter text**, appended as typed (F0.8), for anything else.
2. With no location, no map view and no own filter text, the filter is `m/<range>`, around the callsign's last known
   position on APRS-IS (as the stand-in does now).

### Updating

3. The filter is recomputed when any part changes, and sent with `SetFilterAsync` (F1.1), never with a new login.
4. Map movements are **debounced**: the filter is sent 2 s after panning or zooming stops, and only when the new map
   part differs enough (centre moved more than a quarter of the radius, or radius changed by more than a quarter). A
   pan doesn't send a filter per frame.
5. Sends are limited to one every 5 s; a change inside that window waits and is merged with any later one.

### Seeing it

6. **Filter circles** (Settings › Map, and a map layer toggle; off by default): each range part as a faint circle in
   the accent colour, so it's clear what the server is sending. The circles use theme tokens and the palette's
   contrast (F0.6).
7. The current filter text appears in the connection's tooltip and in Settings › Profiles for the active profile, for
   anyone who wants to check it.

### On a gateway

8. One gateway has one APRS-IS login, but every browser has its own map view. By default, a gateway's filter uses only
   **my range, followed and tracked stations and the profile's text**, not viewers' map views, so an anonymous
   viewer can't widen what the station receives.
9. **`Gateway:FollowViewers`** (off by default) adds viewers' map parts: one range part per connected viewer, up to 8
   (APRS-IS accepts at most 9 range parts, and my range is one), each capped at 500 km, dropped when the viewer
   leaves; the most recently moved views win. For a club where everyone may steer the station.

## Service surface

- The UI reports its map view to the engine: `SetMapViewAsync(centre, radiusKm)`, debounced as in behavior 4. On a
  desktop it is the window's map; on a gateway it is ignored unless `Gateway:FollowViewers` is on.
- `EngineStatus` gains `Filter` (the text currently sent) for behavior 7.
- The profile gains `RangeKm` (default 150).

## APRS.NET dependencies

- **G04, typed filter builder** (range, friend range, buddy list, my range, raw parts): delivered (`0.2.0-alpha.2`,
  `AprsNet.Filters`); the stand-in already uses it.
- **G08, geodesy**: the view's radius from its corners, and the 1,000 km cap.
- **G03** (delivered, `0.1.0-alpha.17`): `SetFilterAsync` on the live connection, kept across reconnects.

## Desktop vs web differences

| | Desktop | Web |
| --- | --- | --- |
| Map view part | The window's map | Only with `Gateway:FollowViewers`, one part per viewer |

## Acceptance tests

1. With a location and range 150: `r/<lat>/<lon>/150` plus the profile's text; with range 0, no range part.
2. Panning outside my range adds a map part 2 s after the pan stops; small moves don't resend; zooming wider than
   1,000 km drops it.
3. Following a station adds `f/CALL/150`; stopping removes it. Tracked stations add `b/CALL1/CALL2`.
4. Sends are at most one per 5 s and never trigger a new login (fake connection counts logins).
5. On a gateway without `FollowViewers`, a browser's map view changes nothing; with it, up to 8 viewer parts, each
   capped, and never more than 9 range parts in all.
6. Filter circles draw each range part in every palette.

## Decisions for review

1. **Gateways don't follow viewers' maps by default** (behavior 8). Proposed: yes, because anonymous viewers would
   otherwise steer the station's feed.
2. **The 1,000 km cap** on the map part. Proposed: yes; beyond that a filter returns most of a continent, and the
   full feed is better asked for explicitly with the profile's own filter text.

## Sources

- APRS-IS server-side filter commands, <https://www.aprs-is.net/javAPRSFilter.aspx> (accessed 2026-10-15): range
  `r/lat/lon/dist` in km, my range `m/dist`, friend range `f/call/dist`, buddy list `b/call1/call2…` (wildcards
  allowed); parts are separated by spaces and a packet passes when any part matches; at most 9 range and 9 friend
  parts; a live connection changes its filter with a `#filter` line.
- Reference capabilities: [functional-inventory.md §3](../reference/functional-inventory.md) (range around my position
